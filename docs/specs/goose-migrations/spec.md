# 规格：以 Goose 管理 RCC 控制表迁移

状态：D-001～D-005、验收入口、AC-001～AC-015、非目标及三工单串行拆分均已由用户确认，进入发布与实施。

## 问题陈述

部署者目前需要区分新安装 SQL、历史编号脚本和特殊维护命令，靠操作记录判断数据库已经升级到哪里。重复执行一次性脚本可能失败；仅见到表存在也不能证明列、索引和约束正确。随着控制结构持续变化，部署需要可查询的迁移进度、明确的存量接管方式和失败后的恢复入口。

## 解决方案

用 Goose 统一 RCC 控制表的新安装和后续向前升级。部署者通过独立维护命令查询状态、升级新库或已接管库、接管经过结构校验的现有库，以及在核查失败原因后显式恢复。Admin 只检查版本、迁移状态与结构；本地 Compose 先完成迁移，再加载开发 fixture，最后启动 Admin。

存量接管以本次功能冻结的当前主分支控制结构为基线。更旧的库先按现有历史流程升级，不重放整条历史迁移链推测进度。只管理 RCC 自有控制结构，保留既有业务表及其数据、账号和发布历史。范围对应 PM-050 的数据库迁移部分。

## 用户故事

1. 作为部署者，我想用统一命令初始化新库，以便不再维护另一份当前初始化定义。
2. 作为部署者，我想知道数据库已应用和仍待应用的迁移，以便决定是否开始部署。
3. 作为部署者，我想升级只执行尚未完成的迁移，以便重复运行不会重复修改数据。
4. 作为维护者，我想接管已有的当前结构，以便从现在开始可靠记录迁移版本。
5. 作为维护者，我想在接管前校验列、索引、约束和引擎，以便错误结构不能被登记为成功。
6. 作为维护者，我想让已有账号、会话、规则和发布历史保持原样，以便迁移管理的引入不改变业务状态。
7. 作为旧版本部署者，我想得到明确的历史升级指引，以便先到达受支持的接管基线。
8. 作为部署者，我想显式执行升级，以便业务进程不持有隐式改表职责。
9. 作为部署者，我想让两个并发升级进程互斥，以便它们不会重复执行同一迁移。
10. 作为部署者，我想在锁等待超时时获得失败结果，以便部署任务不会无限挂起。
11. 作为维护者，我想在数据库不可用或权限不足时得到安全诊断，以便明确处理原因。
12. 作为维护者，我想识别部分成功或执行结果未知，以便不把中断误当作未执行。
13. 作为维护者，我想核查后显式恢复，以便下次部署不会擅自重试不确定的改表操作。
14. 作为维护者，我想只使用向前修复，以便不会因通用 down 删除账号或配置历史。
15. 作为部署者，我想让版本落后、异常或结构不匹配的 Admin 拒绝就绪，以便部署不能误报可用。
16. 作为部署者，我想让已经启动的 Admin 继续报告迁移异常，以便现有就绪探针能发现问题。
17. 作为维护者，我想在 Admin 无法就绪时仍可使用迁移和既有维护命令，以便能够恢复系统。
18. 作为管理员，我想让迁移账本受到控制表保护，以便普通配置接口不能读写它。
19. 作为开发者，我想让本地 Compose 自动按迁移、fixture、Admin 的顺序启动，以便新库和旧数据卷都能重复验证。
20. 作为开发者，我想把开发样例保持在独立 fixture 中，以便生产迁移不写入样例业务配置。
21. 作为维护者，我想保留历史升级与维护说明，以便旧库仍有可执行的接入路径。
22. 作为后续开发者，我想让新增控制结构只进入 Goose 迁移，以便新安装与升级后的结构一致。

## 验收入口

主要入口为部署者使用的公开迁移维护命令，观察退出码、迁移状态及安全诊断；命令连接真实 MySQL 8.4。状态、向前升级、接管、显式恢复是四种可观察操作，具体命令拼写在实现时统一。

必要的系统入口为现有 Admin 外部进程启动与 HTTP 就绪检查，以及真实 Compose 启动流程。只在验证数据保留、物理结构、锁竞争或部分 DDL 成功等公开输出无法独立证明的事实时，使用隔离数据库的只读断言。无前端交互变更，不新建迁移 Web 页面或测试专用 HTTP 接口。

## 验收用例

### AC-001：新库初始化

- **Given**：目标数据库中没有 RCC 控制结构，数据库可连接且维护权限满足要求。
- **When**：运行向前升级操作。
- **Then**：创建完整控制结构并登记成功版本，状态查询显示达到本发行要求；不创建或修改使用者的业务表，也不写入开发 fixture。
- **证据**：真实命令与 MySQL；控制结构和版本状态独立核对。
- **层级**：契约/集成。

### AC-002：后续向前升级

- **Given**：库已成功应用已知旧版本，下一测试发行包含合法的后续控制结构迁移。
- **When**：运行新发行的向前升级操作。
- **Then**：只应用尚未完成的迁移，状态达到新版本；既有数据保留，结果与同一发行的新安装结构一致。
- **证据**：两个测试发行通过相同公开命令升级；实际结构和固定数据比较，不为验收新增无业务意义的生产字段。
- **层级**：契约/集成。

### AC-003：状态查询与重复运行

- **Given**：分别存在未接管库、已成功升级库及重复调用场景。
- **When**：查询状态，或对成功库重复升级。
- **Then**：状态查询不修改数据库；重复成功操作不重新执行已完成变更或重复登记，不重置业务状态，并明确显示当前结果。未接管库不能被普通升级操作静默接管。
- **证据**：公开命令前后版本及数据快照对比；未接管状态与操作拒绝。
- **层级**：契约/集成。

### AC-004：接管当前存量库

- **Given**：没有 Goose 成功记录，控制结构符合冻结基线，并有账号、会话、规则、记录版本与发布历史。
- **When**：运行显式基线接管。
- **Then**：完整校验后登记基线；不重跑历史改表或回填，不重置管理员授权、控制游标和既有数据；随后可正常查询状态与升级。重复接管返回已接管结果，不重新登记或改写原有历史。
- **证据**：真实接管命令；独立结构比对、固定历史数据与现有账号/发布公开读取回归。
- **层级**：契约/集成。

### AC-005：不兼容结构拒绝接管

- **Given**：待接管控制表出现代表性的缺表、缺列、额外不兼容列、类型/默认值/索引/CHECK/引擎不匹配，或必要控制元数据不完整。
- **When**：运行基线接管。
- **Then**：非零退出并指出需要处理的结构问题，不登记成功基线，不修改已有业务或控制数据；仅能查询部分表不能代替完整验证。
- **证据**：真实 MySQL 代表性结构损坏及公开拒绝结果，核对原数据和成功状态未变化。
- **层级**：契约/集成。

### AC-006：旧库的历史升级边界

- **Given**：库仍处于不受接管支持的历史结构。
- **When**：尝试接管，再按既有流程升级到冻结基线并重新接管。
- **Then**：首次明确拒绝并给出历史升级指引，不擅自重放旧脚本；完成历史升级后可以接管，历史归属与既有维护保证保留。
- **证据**：代表性旧库通过历史 SQL 和 Policy 维护入口升级，再执行公开接管命令。
- **层级**：契约/集成。

### AC-007：依赖不可用与诊断

- **Given**：数据库不可用、连接超时或所需维护权限不足。
- **When**：执行状态或迁移操作。
- **Then**：有界失败并返回非零退出码和可操作的诊断；不报告迁移成功，日志不泄露密码、连接串或业务数据。若已经开始写入，则按 AC-009 的不确定状态处理。
- **证据**：真实连接失败、超时与权限限制下的公开命令结果。
- **层级**：契约/集成。

### AC-008：并发迁移

- **Given**：两个独立进程同时操作同一库，其中一个正在迁移或接管。
- **When**：另一个尝试升级、接管或恢复。
- **Then**：互斥执行；等待有界，超时者非零退出且不介入执行者的操作。锁可用后重新运行按真实状态继续，不能重复已完成变更。
- **证据**：真实 MySQL 与双进程竞争，观察状态、退出码及实际持久效果；包含首次建库的竞争。
- **层级**：系统关键路径。

### AC-009：失败、中断与结果未知

- **Given**：迁移在开始后发生错误、部分 DDL 已成功后进程中断，或数据库已保存成功版本但进程尚未报告成功时中断。
- **When**：维护者查询状态并再次运行普通升级或部署。
- **Then**：报告实际可知进度及未确认状态，不把部分成功宣称为整体回滚，也不把未知结果当作未执行；普通部署不得自动重试未确认迁移，必须先进入显式恢复流程。已有业务数据不因清理而丢失。
- **证据**：真实 MySQL、进程中断或系统边界故障注入及重启；分别核对结构与持久状态。
- **层级**：系统关键路径。

### AC-010：维护者显式恢复

- **Given**：存在失败或未确认操作，维护者已按诊断核查当前结构及版本。
- **When**：调用显式恢复操作，随后查询状态或再次升级。
- **Then**：只有在恢复条件满足时才允许安全重试或确认已经完成的结果；无法证明时仍拒绝并保留诊断。不能用删除历史、强行跳版本或忽略实际结构冒充恢复；不提供 down、reset 或强制标成功入口。
- **证据**：AC-009 的代表性故障经真实恢复操作转为成功；不满足条件时仍被拒绝，原账号、规则和发布历史保持一致。
- **层级**：契约/集成。

### AC-011：Admin 只读就绪门禁

- **Given**：数据库分别处于未接管、已知旧版、当前完整、未知/超前版本、迁移未确认及版本虽正确但必要结构损坏的状态。
- **When**：启动 Admin，或通过现有就绪接口检查运行中的 Admin。
- **Then**：只有本发行支持且完整、无未确认迁移的状态通过；其余启动/就绪拒绝并给出维护指引。Admin 不执行升级或登记版本，不自动修正结构；成功恢复后可重新通过就绪检查。
- **证据**：真实外部进程与 HTTP 就绪检查；限制业务进程 DDL 权限并核对检查前后的数据库状态。
- **层级**：系统关键路径。

### AC-012：迁移控制结构不可作为业务表访问

- **Given**：存在迁移版本及恢复状态等控制结构，调用方使用正常管理接口。
- **When**：发现业务表，或尝试配置和访问这些控制结构。
- **Then**：迁移结构处于 RCC 控制表保护范围，不能经通用配置接口暴露或修改；正常受管业务表不受影响。
- **证据**：现有公开 HTTP 表发现、规则绑定与数据访问的真实 MySQL 回归。
- **层级**：契约/集成。

### AC-013：维护入口不依赖 Admin 就绪

- **Given**：Admin HTTP 配置缺失、控制结构待升级或 Admin 无法就绪，数据库维护连接可用。
- **When**：使用迁移维护入口及既有账号/Policy 维护流程。
- **Then**：独立维护连接可以执行该阶段合法的操作；迁移接管不替代管理员显式授予、账号恢复、记录维护基线推进或发布所需权限，权限不足仍明确拒绝。
- **证据**：现有维护连接进程测试与真实数据库，结合新命令的独立执行。
- **层级**：契约/集成。

### AC-014：Compose 部署顺序与失败阻断

- **Given**：新数据卷、已接管卷、未接管的当前结构卷及未确认迁移卷。
- **When**：按文档启动本地 Compose；存量未接管卷先显式执行接管。
- **Then**：新库和已接管库依次完成 Goose 迁移、开发 fixture、Admin；失败或未接管/未确认状态阻止后续启动。重复启动不重复修改成功数据，修复后恢复正常。
- **证据**：真实镜像构建与隔离 Compose 进程，检查服务结果、就绪状态和已有数据保留。
- **层级**：系统关键路径。

### AC-015：统一当前初始化来源并保留历史职责

- **Given**：功能已经完成部署接线。
- **When**：通过当前文档、构建产物和测试初始化新库、升级库，或执行旧库历史升级。
- **Then**：当前生产和开发新安装均使用同一 Goose 迁移来源，旧当前初始化入口已删除；旧版本 SQL 及必要测试历史快照仅用于已说明的历史职责。开发 fixture 独立且不进入生产迁移；初始化和升级所得当前结构一致。
- **证据**：入口引用检查、新安装/升级结构等价集成测试、历史升级回归及 fixture 隔离检查。
- **层级**：契约/集成。

## 故障与一致性决策

- MySQL DDL 可能部分成功；成功版本、迁移尝试状态和实际结构需要分别核对，不承诺整份 DDL 文件可由事务回滚。
- 开始变更后留下的失败或不确定状态阻止普通部署继续；恢复是维护者显式动作，不能通过忽略账本或清空控制数据恢复。
- 所有会改变迁移状态的操作在同库互斥并有界等待；只读状态查询不能因查询本身创建账本或登记基线。
- 正常重复升级与重复接管返回既有结果；未接管存量库不能被普通升级隐式接管。
- 新版本账本不能取代结构验证，也不能取代已有停写窗口、授权和业务记录维护要求。维护期间仍按部署流程停止旧 Admin 与外部写入者；迁移锁只协调迁移进程，不宣称能阻止任意外部 SQL。
- 数据库不可用时不推断成功或失败的持久结果；诊断区分操作尚未开始与需要核查的未知结果。
- 本期不引入外部消息、跨库事务或后台自动恢复，不为这些无关依赖设计补偿。

## 实现决策

- 使用固定版本的 Goose 管理 MySQL 控制结构，通过独立维护入口提供状态、向前升级、基线接管与显式恢复。
- 将本功能开始时的已发布控制结构冻结为接管基线；接管校验列、类型、默认值、索引、约束、引擎及必要控制元数据。接管允许保留使用者的既有业务表。
- 新安装和后续迁移来自唯一 Goose 定义；历史一次性脚本不被改写为可任意重放的 Goose 历史。
- 迁移账本及必要恢复元数据处于受保护的 RCC 控制表范围，不改通用业务表 Schema 所有权。
- 明确配置数据库级迁移互斥和有界超时，不依赖 Goose 默认提供锁；迁移连接与正常业务连接职责分开。
- Admin 检查本发行要求的版本、迁移状态和必要结构，检查只读；旧业务进程按维护窗口要求停止。
- 迁移失败后的持久状态须覆盖新安装、中途升级和成功记录已保存但结果未确认等窗口；本期迁移必须有经过验证的恢复条件。后续迁移按同一恢复约定编写，不能依赖通用 down。
- 既有维护命令、生产账号及权限配置继续承担原职责。Compose 的迁移任务使用维护权限，不要求业务启动隐式提升权限。
- 不改前端界面，不把内部迁移实现细节放进普通配置操作流程。

## 测试决策

- AC-001～AC-015 均需自动化证据；优先复用现有真实 MySQL、维护命令及进程测试基础设施。手册的故障恢复演练作为补充，不替代自动化证据。
- 主要测试通过迁移命令的公开行为验证退出码和状态，不断言内部 Goose 调用次数、私有方法或具体驱动错误文字。
- 物理结构等价、实际部分成功、锁竞争和历史数据保留用真实 MySQL 独立验证；以固定预期结构与测试数据为依据，不由待测实现计算自身期望值。
- 系统级测试聚焦双进程互斥、中断恢复、Admin 启动/就绪和 Compose 顺序，避免每层重复同一断言。
- 若结构签名规范化存在复杂纯规则，可增加局部模块测试；不能以模拟自有内部协作者代替真实结构验收。
- 新命令纳入构建与适当的 CI 检查，Go 完整测试、相关真实 MySQL 回归、历史升级和既有账号/发布行为必须继续通过；所需真实依赖不可用时明确报告阻塞。

## 临时结构与退出条件

迁移命令交付到部署切换期间，当前初始化 SQL 暂时与 Goose 新安装路径并存，以保持既有调用方可运行。最后一张部署切换工单负责迁移全部当前调用方、删除旧当前初始化入口及重复维护的定义，并用引用检查和结构等价验收证明收缩完成。

冻结的历史升级 SQL、旧库测试快照及必要历史维护命令有永久且明确的旧库职责，不充当当前初始化备用通路；保留它们不代表要求所有旧版本可由 Goose 自动升级。无双写、Feature Flag 或绕过就绪检查的长期兼容开关。

## 上下文影响

- ADR-0024 记录经过验证的基线接管、独立升级、向前恢复和统一初始化决定，保留 ADR-0001 的业务表结构边界。
- 更新架构、部署、迁移、Admin 启动/就绪与恢复契约，以及新增迁移的开发约定。
- 若需要命名迁移结构版本，明确其与 Record Version、Release Order Version、Table Version 的区别；不把 Goose 表名、命令或进度写进领域词汇表。
- 功能完成后更新 Notion PM-050 的已交付迁移范围和验证证据；其余生产化工作保持真实状态。

## 超出范围

- 业务表 Schema 设计、自动修改业务表、任意 SQL 的 Web 入口或数据库设计器。
- Goose 直接升级所有历史版本；自动猜测并修复任意未知存量结构。
- down、reset、自动删表、清空历史、强制跳版本或自动恢复未知迁移。
- 零停机升级承诺、备份平台、安全扫描、多数据源、PostgreSQL 或 PM-050 的其他生产化能力。
