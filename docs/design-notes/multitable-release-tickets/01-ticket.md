# T1：三表存储下的原单发布与回滚

状态：用户已确认切片及依赖；ready-for-agent。

## 父工单

Part of #81：https://github.com/asherzj/relational-config-center/issues/81

## 要构建什么

先以现有单表混合变更跑通完整流程：主单、变更明细和成功执行分开存储，审批发布后在原单预览并一次确认倒序回滚，结果仍在原单查看。直接替换独立回滚单行为，为后续多表扩展提供可运行基准。

## 验收标准

- [ ] 三类业务表分别承担流程、逐项申请/实际结果、成功执行摘要；不建立执行结果明细表，不复制整单大JSON保存执行明细。
- [ ] 普通发布与回滚复用真实执行器，发布正序、回滚倒序；实际结果、版本、通知、主单及占用在同一事务保存。
- [ ] 无新审批或必填原因即可在未完结原单回滚；已完结/已回滚被拒绝，成功留在原单并显示原发布和逆向结果。
- [ ] 原申请和审批保留，执行记录最多发布/回滚两条；不同执行的命令和通知归属不能因共用主单号而互相覆盖。
- [ ] 保留必要状态、权限、原子失败及幂等回归；不得先删一致性保护等待后续补回。
- [ ] 首次切换提供可运行的新表结构和API/UI读写；无需旧单数据兼容或业务数据双写。

## 验收用例

唯一主要交付：AC-010。采用父规格Given/When/Then；其他相关用例是必要的回归和跨切片证据，不重复分配主要责任。

## 验证证据

真实MySQL+HTTP证明单表混合变更的原单恢复、两种执行的版本/命令/通知及全事务结果；浏览器证明一次确认、结果留在原单、原申请与实际结果可区分，含390px。存储结构检查证明没有新建独立回滚单或执行结果明细表。

## 临时结构与退出条件

本阶段只承诺现有单表范围的完整路径，多表由T3交付。任何为逐步改造保留的单表默认字段、旧内部结果外观只能映射新存储，禁止旧数据兼容或双写；T3解除单表业务限制，T7负责清除剩余外观和旧结构。新旧回滚业务路径不并存。
