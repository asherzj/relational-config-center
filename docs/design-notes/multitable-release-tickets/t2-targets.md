# T2 / #83 实现与 T3 接缝

`ReleaseItem.DetailID` 是持久的单内身份，`TableName` 是显式明细表名。`DraftChanges` 只接受 `upserts`、`delete_detail_ids`、可选完整 `detail_order`；保留未提及明细的快照与基线，最后检查完整结果的 1000 条上限与同表主键重复。`items` 是仍受支持的明确原子整单替换接口，不是新增过渡外观。T3 解除单表约束后应按每个明细表取得快照；不能以主单表名推断所有目标。

保存事务依次锁请求、已有主单/实际明细键，取得涉及 Table Policy 的共享行锁，然后准备本次内容，将明细、完整目标及未结束表引用替换、成功结果一同提交。共享锁必须早于第一个一致性读，包括 Query/Mutation Policy 目录读取。发布和原单回滚取得表进度行锁及 Table Policy 排他行锁，再读取执行元数据和基线，并将锁持有至业务写入、执行记录、目标释放及请求结果一同提交；因此回滚先开始时草稿等待并读取提交后的旧值，草稿先读取时实际写入等待。不同表执行相互独立，同表草稿仍可并发；这是短事务读写互斥，不是拒绝同表不同目标的保存。提交另行比较持久申请的 `before` 与真实原值，外部 SQL 即使未递增平台版本也不能静默改写申请基线。

T3 多表必须先按稳定表名顺序取得**全部**相关规则/执行锁，再建立任何目录或业务基线快照；不能先读取 A 再等待 B。规则替换取得单表规则排他行锁，使用 `SELECT ... LIMIT 1 FOR SHARE` 当前读检查未结束引用；它不锁主单、不插引用，所以不形成规则→主单与主单→规则循环，也不依赖较早的 RR 快照。引用与目标读取不锁空范围；精确插入/删除在主单互斥内执行。

提交同时校验持久申请的主键表/键和附加键集合；外部 DDL 即使只改变 collation、没有改变原值或平台版本，也不能让提交静默冻结尚未占用的新键。此时返回带明细位置的 `record_version_conflict`，由用户显式重新保存草稿走完整原子目标替换；如新键已有别单占用，仍保留旧申请和旧目标并返回占用冲突。

`ReadConcurrencyKeys` 复用 `columnIdentityMetadata` / `recordLookupExpression` / `recordWeightExpression`，MySQL 按真实字段类型和 collation 计算 `WEIGHT_STRING`。每个分量编码字段名长度/名字、NULL 标志或非 NULL 长度/权重，以 `rcc-concurrency-key-v1\0` 命名空间 SHA-256。NULL 与空字符串及组合边界不碰撞；表名由目标表列隔离。配置在未结束引用期间不可改变，因此无需并存多个键定义或版本。主键原编码保持不变。

`ReplaceReleaseTargets` 先取得排序后的完整新集合（允许当前单已有所有权），全部成功后才按精确旧键删除不再需要的目标。失败会回滚内容、版本、目标、表引用和幂等请求。它按完整集合去重，所以同单共享业务键直到最后一项移除才释放。`rcc_release_table_references` 单独记录未结束明细的表，覆盖自增主键未确定且没有附加键的草稿。所有终态共用 `ReleaseTargets` 释放两种目标和引用；生成主键仍由发布后实际结果加入。
