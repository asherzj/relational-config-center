# Admin 到 Server 的配置变更传播方案备忘

## 状态

- 用途：后续 Admin 到 Server 通信技术方案选型的候选方案。
- 当前结论：尚未选型，不构成 ADR 或实现承诺。
- 实现状态：不在当前迭代实现。

## 方案概述

MySQL 中的当前配置表是配置的最终事实来源（source of truth）。在此基础上，维护一张追加写入的配置变更日志和一个单调递增的全局 `revision`，供各 Server 实例可靠地增量同步配置。

广播通知只负责降低变更感知延迟、唤醒消费者，不承担可靠投递职责。即使通知丢失，Server 仍可通过定时轮询全局版本实现最终一致。

## 写入路径

每次新增、修改或删除配置时，Admin 在同一个 MySQL 事务中完成：

1. 更新当前配置表；
2. 写入一条配置变更记录，至少包含配置键、操作类型以及应用该变更所需的内容；
3. 推进全局 `revision`。

事务通过锁定全局版本行串行分配 `revision`，确保版本分配顺序与事务提交顺序一致。配置表更新、变更日志写入和版本推进必须一起提交或一起回滚。

## 消费路径

每个 Server 实例维护自己的消费游标，并执行以下循环：

1. 定时读取并比较全局 `revision` 与本地游标；
2. 发现新版本后，按 `revision` 升序分页拉取游标之后的变更记录；
3. 按顺序应用变更；
4. 仅在变更成功应用后推进本地游标。

可额外广播变更通知以立即唤醒 Server，但通知内容不是事实来源，通知丢失也不能阻断后续同步。

## 启动与恢复

Server 重启时可以选择：

- 从持久化的实例消费游标继续拉取增量；或
- 在一个一致性事务中读取全量配置及与该快照对应的全局 `revision`，以该版本作为新游标，再继续消费后续增量。

变更日志允许按保留策略定期清理。如果某个 Server 的本地游标早于当前最早保留的 `revision`，该实例不得跳过缺失区间，必须重新执行全量同步。

## 需要在选型时确定的事项

- 配置键和不同操作类型所需变更内容的具体格式；
- 变更记录保存完整新值、差异，还是仅保存用于回读当前配置的标识；
- Server 实例游标的持久化位置、实例身份和失效游标清理方式；
- 分页大小、轮询周期、失败重试、幂等应用和监控告警策略；
- 广播通知的具体传输机制；
- 变更日志的保留周期，以及清理时如何判断仍有消费者需要旧版本；
- 全量快照读取对大数据量、长事务和 MySQL 资源的影响。

## 必须保持的不变量

- 当前配置表始终是最终事实来源，变更日志不是事件溯源模型中的唯一状态来源。
- 任一已提交配置变更都有唯一、单调递增的全局 `revision`。
- 消费者严格按 `revision` 顺序应用增量，成功应用后才推进游标。
- 正确性不依赖广播通知的可靠性。
- 增量历史出现缺口时通过全量同步恢复，不能静默跨过缺失版本。
