# 规格：管理台正式发布闭环

状态：用户已确认业务决定、验收入口、48 条编号用例、非目标、8 张工单拆分及逐单实现/验证/评审/提交推送和关闭交付工单。所有证据均为待执行的验收要求，不表示测试已通过。

## 问题陈述

当前管理台在确认字段差异后直接修改配置记录，没有由另一人审批的发布流程，也没有可追溯的发布结果、可靠的重试身份或回滚申请。用户无法保证获批内容与最终写入一致，旧申请可能覆盖新的修改，网络中断时也难以判断是否已经写入。

## 解决方案

将配置记录的所有 ADD/MODIFY/DELETE 统一改为发布单：编辑者保存单表草稿，提交冻结内容，由另一位有审批权限的用户批准，再由发布者手动执行。数据、记录版本、最终态发布变更记录、表发布版本、操作历史及刷新通知记录一起提交；任何环节失败都不留下部分发布。回滚是需要重新审批的反向发布单，不能覆盖后续修改。

首版沿用当前单 MySQL Managed Data Source、受管表、规则目录、本地账号和登录会话，不引入 Environment 或 Page Model。角色为全局可组合授权；新老账号默认只读，维护命令指定首位 ADMIN，管理台完成后续分配。规则目录由 ADMIN 直接管理，不进入发布单审批。

发布成功仅表示数据库提交成功。刷新通知记录持久化但本期不投递；灰度、Server/Client 分发和版本大盘另期交付。

26. 作为审批人，我想回滚也通过正常审批，以便撤销配置同样经过第二人确认。
27. 作为发布者，我想回滚遇到后续修改或新约束时拒绝执行，以便不损坏较新的配置。
28. 作为查看者，我想长期检索发布历史和已取消草稿，以便追溯全部变更过程。
29. 作为部署维护者，我想安全升级存量账号和配置数据，以便切换后旧 API 无法绕过审批。
30. 作为维护者，我想真实数据库和浏览器证明完整流程，以便测试成功代表实际链路可用。

| AC-041 | 一张已发布单的结果尚未被后续修改 | 申请反向草稿，经他人审批后发布 | 原单标记已回滚并关联新单；业务值恢复，产生新的变更和版本；未审批不能回滚，原历史保留 | 单条及混合批量的真实反向发布路径 | 契约/集成 |
| AC-042 | 原单发布后记录又变了，或恢复内容违反当前约束 | 创建/提交/执行回滚单 | 拒绝回滚，不覆盖较新配置；任一项冲突整单零副作用，原单不虚标已回滚 | 后续修改、删除重建和新约束集成 | 契约/集成 |

| AC-044 | 同一原单已有回滚申请或已成功回滚 | 并发申请、重复执行或重新查询关联单 | 同一请求返回同一单；同一原单不发生重复有效回滚；关联历史与原单状态一致，可取消未发布申请后重建 | 真实并发与回滚请求幂等 | 契约/集成 |

## 故障与一致性决策

1. **持久化边界。**发布事务包含业务记录、记录版本、最终态 Publication Command、Table Version、发布单状态、操作日志、在途占用释放及刷新通知记录。回滚发布还包含原单与反向单的状态关联更新。任意步骤失败全部回滚；网络调用不得进入事务。
2. **明确失败。**未提交的发布失败不新增一个含糊的持久化 FAILED 状态，发布单保持 APPROVED 及原版本/占用。返回稳定错误，区分内容、权限、冲突与依赖故障；用户不能通过重试跳过版本或规则检查。失败诊断不写成成功操作历史。
3. **结果未知。**COMMIT 或网络返回不确定时，前端显示“结果待确认”，保留原 Idempotency-Key，不自动换键再次执行。恢复后通过请求结果查询或原键重试判断；查不到不能立即推断业务未提交，重试必须与并发中的原请求收敛。
4. **幂等范围。**所有可重试的业务写操作使用账号、操作及 Idempotency-Key 标识，保存规范请求摘要和成功业务结果。同键同内容重放原结果，即使携带原状态版本；同键不同内容返回冲突。鉴权仍按当前身份执行。回滚/约束失败不能占住一个不可恢复的半完成幂等记录。历史和幂等结果本期不自动清理。
5. **两种并发版本。**发布单状态版本控制草稿/审批/取消动作；Record Version 控制业务记录基线。版本及 id 通过 JSON 字符串无损传递，缺失不等于默认接受最新版本。删除后的记录版本保留；存量缺失版本使用明确的初始基线并在首次写入时原子建立，不写业务表版本列。
6. **在途目标。**草稿不占用；提交时一次取得全部已知目标，冲突零残留；拒绝、取消、发布成功时释放。明确失败保持占用，既无到期自动释放，也无忽略在途目标的强制发布。未知自增 id 不按业务字段推断目标；实际新增身份仍受唯一性、记录版本和已有占用校验。
7. **冻结与重验。**提交冻结服务器核实的内容、表结构及变更规则执行语义，执行时重新比较并验证当前授权。元数据名称/描述变化无效力变化；Schema、规则语义或记录版本变化拒绝。已完成的合法审批不因审批人以后停用或撤权自动作废。
8. **可信最终态。**业务写入后在同一事务内读取完整最终行，对新增/修改记录编码；删除记录显式 tombstone。无法完整校验最终字段、身份或附带写入时不得成功。表版本只在完整提交时前进；回滚也创建新版本，不倒退游标。
9. **依赖范围。**当前外部持久依赖为单个 MySQL。刷新通知只持久化，不联系 Server，故本期不承诺远端超时重试、死信或客户端收敛。配置历史不会写进普通日志、指标或底层错误响应。
10. **运维边界。**任意直接 SQL、其他写库应用以及未经维护流程的表重建不在记录版本保护之内；必须在维护窗口停写、保留/更新并发身份并重建所需基线。系统不自动修改业务表 Schema，也不以环境字符串假装数据已隔离。

## 实现决策

### 状态与权限

持久状态为 DRAFT、PENDING_APPROVAL、APPROVED、SUCCEEDED、REJECTED、CANCELLED、ROLLED_BACK。执行过程由原子事务承载，前端请求中状态不新增为可遗留的业务阶段。

| 当前状态 | 允许的操作 | 约束/结果 |
|---|---|---|
| DRAFT | 编辑、提交、取消 | 编辑/提交限申请人且当前有 EDITOR；取消由仍有编辑权限的申请人或 ADMIN；提交后内容冻结 |
| PENDING_APPROVAL | 批准、拒绝、取消 | 他人 APPROVER/ADMIN 作决定，批准或拒绝意见必填；取消按申请人/ADMIN 约束 |
| APPROVED | 执行、取消 | PUBLISHER/ADMIN 手动执行；申请人可在持有发布角色时执行他人批准的单据 |
| SUCCEEDED | 查询、申请回滚 | 新建有关联的反向草稿，不直接写回原内容 |
| REJECTED/CANCELLED | 查询、复制新草稿 | 新草稿重新读取并确认基线，不复制审批 |
| ROLLED_BACK | 查询关联历史 | 原发布及已成功反向发布都保留，不能重复有效回滚同一次发布 |

VIEWER 可读取本部署全部受管表和发布历史；EDITOR、APPROVER、PUBLISHER 各自包含查看能力但不互相隐含其余写能力。ADMIN 管理账号角色和规则目录并拥有业务能力，但仍禁止自批。角色变更实时约束后续请求；已在途认证/事务不承诺被强制撤销。只有角色分配权限不能代替有效 Table Policy；查询和变更仍受当前规则约束。

首位 ADMIN 由维护者明确指定，不根据首位注册者、用户名或邮箱推断。角色 Schema 就绪但尚无 ADMIN 时，注册、登录和只读能力仍可用，先注册明确账号再通过维护命令授予角色，不能造成必须先有管理员才能创建首个账号的循环。新老账号默认为 VIEWER；管理界面不能移除最后一个启用 ADMIN 的管理权，账号维护路径必须配合此不变量并保留恢复手段。角色调整记录永久身份和前后授权。

### 操作与数据契约

- 提供发布单创建/草稿更新、分页列表/详情、提交、批准、拒绝、取消、执行、复制及申请回滚操作。所有修改已有单据的动作携带发布单期望版本；记录明细独立携带记录基线版本。查询提供当前主体的 allowed_actions，服务端仍独立校验。
- 草稿和详情以 `table_name` 关联当前受管表，明细表示 ADD/MODIFY/DELETE、已知或待生成 id、期望记录版本、原始基线和申请值。原值由服务器核实，不能相信客户端上传的 before。保留原意与最终生效值的区别。
- 一单同表、1～1,000 项；同一已知身份只出现一次。不得用请求顺序表达对同一行连续删除/新增。批量所有校验和提交原子执行；配置请求字节、单字段、事务及返回预算，超出时整体拒绝并说明，不偷偷拆成多次发布。
- 列表按表、状态、申请人筛选，支持单号查询和稳定分页。历史可见范围是本部署，含冻结差异、意见、永久身份和关联发布；账号角色页只暴露授权管理需要的资料，不返回凭据或会话秘密。
- 接口使用 401 未认证、403 无权/自批、404 不存在、409 版本/目标/幂等冲突、422 内容/状态/能力无效及现有的依赖错误映射。保留小写稳定 code、message、request_id 风格，不直接复用旧参考的大写内部错误码。移除原记录写路由后明确拒绝旧客户端，不将旧调用静默解释为已发布。
- 业务表自动操作人填写实际执行人的永久 Account ID，自动时间使用数据库时间。申请、审批和执行分别记录；回滚恢复业务字段而不恢复旧操作人/时间，生成列按当前数据库规则计算。

### 事务执行与发布记录

- 复用现有 Schema、Policy Snapshot、Mutation Policy 和数据库类型校验，将“提交一张发布单”作为一个拥有事务的执行能力；HTTP、节点和 UI 不分别安排业务写入、版本推进或日志。
- Record Version 的等价 id 必须与真实数据库身份一致，处理数值规范化、字符比较和删除重建；对表重建/重新接入保留明确的维护代际边界，不能以删除控制行重置旧令牌。复用并补齐已有并发保护 Issue #33，不重建一套独立发布专用行版本。
- 发布变更记录采用显式版本的本期 Admin 单数据源格式，保存规范表定义摘要、完整最终行/删除标记、校验和、原单及顺序信息。SQL NULL 与 JSON 字面量 null、文本 `null`、空串和二进制值保持无歧义；最终态以数据库结果为准。
- 表发布次数、Command 游标、记录并发版本和发布单状态版本分别建模；游标不得以可能乱序提交的自增号直接承诺无缺口可消费。实际消费者尚未接入，本期通过按表事务排序及完整持久记录保留后续接入条件。
- 本期格式不伪造 `environment=production`，也不声称已符合完整 Server 候选协议。未来环境与 Runtime 接入时需要显式协议转换/迁移和真实联调；历史原记录保留。本期发布次数或时间不冒充未来大盘的 MD5、source_updated_at 或缓存版本。
- 支持可校验的默认值、生成列和目标行触发器结果；如触发器/级联导致无法枚举的额外记录变化，能力检查在业务写入前拒绝。不可通过只记录显式目标而忽略附带写入来满足“所有变化都有记录”。
- 已批准单失败仍保留占用；取消与执行、重复执行以及反向发布对原单的标记在受控事务中竞争。回滚申请关联原结果和版本，不从当前值偷偷生成能覆盖新变化的反向基线。

### 界面与恢复

沿用现有组件、字段输入、Change Set、未保存保护和账号恢复行为。数据页确认变更后进入草稿；发布单页提供列表、明细、冻结差异、操作历史和当前可执行动作。单条先交付，再扩展同表明细集合和勾选批量删除；首版没有文件导入。

冲突保留输入，用户先查看最新数据再明确重建。未知结果保留原请求标识，跨刷新/登录恢复时以账号隔离，不能在切换账号后重放上一账号的请求。界面区分“草稿已保存”“待审批”“已批准”“已发布”和“结果待确认”，数据库成功时通知显示“分发尚未接入”，不展示消费者已生效。

## 测试决策

- AC-001～AC-048 均需可重复的自动化或明确系统验证证据；没有无法观察业务结果的模拟验收。权限、状态、冻结与幂等以 HTTP 公共行为为主；复杂 Codec/状态转移局部规则使用固定样例和行为测试，不复制同层断言到所有层。
- MySQL 8.4 集成独立证明真实身份比较、版本/目标竞争、最终行、约束失败和事务回滚。使用真实依赖边界故障注入，不 mock 自有内部协作者；必要依赖缺失属于未完成，不将 skip 记为通过。
- 浏览器主要证明账号角色管理、数据页到发布单、三角色发布与回滚、结果未知恢复、输入保留、键盘/弹层及窄屏操作。各行为工单随实现包含自己的定向 UI/HTTP 证据；最终工单只补跨工单的真实整链路和升级证据。
- 运行既有 Go 全模块测试/构建、Web 测试/类型检查/生产构建及完整 MySQL 集成。扩展正式浏览器入口以实际包含发布单验收，不能沿用只匹配旧账号测试函数的过滤表达式。
- 保留现有 Admin 依赖方向机器检查；增加或更新发布 HTTP 契约、控制表保护和“无旧直写调用”的检查，确保公共接口变化与架构边界有机器证据。
- 每个交付工单以固定基点和本规格做 Standards/Spec 两轴评审；仅在本单必要检查通过后提交、推送并发布证据。全功能交付后逐 AC 汇总真实证据和未决问题。

## 临时结构与退出条件

1. **旧记录直写入口。**在并发保护和草稿/审批逐步落地时暂留，保持旧界面可用且维护统一记录版本；单条正式发布工单 T5 负责同时迁移数据页、脚本/用例并删除旧 HTTP 写入口和 Web 写调用。T5 不能仅隐藏按钮或给旧路径留兼容放行。功能整体完成前不得将中间分支宣传或部署为已经强制审批的版本。
2. **单条容量阶段。**T3～T5 只先允许一个明细以便独立验证；T6 删除该临时上限，交付 1～1,000 项混合批量及界面组织能力。不得保留用户可见的单条专用兼容流程。
3. **无实际通知投递。**这是已确认的本期产品边界，持久化通知记录为正式数据，不是假成功适配器或临时 mock。实际 worker 和消费者属于未来工作包，本期不新增一个声称能够投递的替代实现。
