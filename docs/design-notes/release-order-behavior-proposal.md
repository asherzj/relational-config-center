# 管理台正式发布闭环：业务规则建议

状态：Q-005～Q-008 对应选择及后续八项边界已经用户确认，见 `release-order-discussion.md` 的 D-005～D-016。本文保留综合来源，正式交付范围以待确认的 `release-order-specification.md` 为准；本文不是发布或完成证据。

## Q-005：一张发布单承载什么

建议一张单对应一张现有受管表，包含 1～1,000 项变更，可混合新增、修改和删除；一次发布全部成功或全部失败。首版不跨表。

- 数据页单条编辑可以创建单条草稿，也可以将变更加入该表的一张自己的草稿；草稿详情可继续添加、编辑和移除明细，支持勾选多行批量删除。JSON/CSV 文件导入另期交付。
- 同一单内相同已知 id 只能出现一次，不接受对同一行“先删再加”等依赖顺序的变更链。
- 修改和删除以已读取记录及其并发版本作为基线；明确填写 id 的新增按该 id 判定目标。已知目标在提交审批时被占用，未结束的另一张单不能再提交同目标变更；草稿不长期占用目标。
- 新增省略自增 id 时，还没有可占用的记录 id。此时承诺同一幂等请求不重复建单/写入，并由数据库唯一索引检查业务唯一性；首版不猜测哪些字段代表同一个业务目标，也不把相似内容的两个独立请求当成同一新增。最终新增 id 由发布事务记录。
- 记录 id 的等价表示必须按数据库真实记录身份收敛，不能产生多个版本或目标占位；属于实现与真实 MySQL 验证责任。

## Q-006：草稿、审批、发布和取消

建议采用一个固定流程：草稿 → 待审批 → 已批准 → 已发布。首版不建设模板编辑器、多级审批、应急免审批或定时发布。

- 创建后为草稿；仅申请人可编辑自己的草稿，且需要编辑权限。草稿编辑版本受并发保护。
- 提交审批前查看完整变更并确认；服务端重验内容、规则和记录基线，冻结本次提交的表结构、规则和内容。提交后不能修改内容。
- 一名有审批权限且不是申请人的用户批准即可；批准和拒绝均填写意见。审批人与执行发布人可以是同一人。
- 有发布权限的人执行已批准的单据；申请人若有发布权限，也可执行别人批准的自己的单据。执行仍按当时身份、状态和数据条件重新校验。
- 审批拒绝后该单结束。可以复制为新草稿，重新读取当前记录、查看差异并再次提交；不能把旧审批带到新单。
- 发布前，申请人或 ADMIN 可以填写原因取消自己的单据/任意单据；普通审批人不代替申请人修改或取消内容。执行与取消同时到达时，只能有一个生效。
- 成功是业务数据和变更、版本、日志、通知记录已经在数据库一起提交。界面明确显示通知待后续分发，不能显示 Server/Client 已生效。
- 数据库明确拒绝或事务回滚时，单据仍处于可重试的已批准状态，错误不伪装成成功；重试不跳过检查。已经提交但响应丢失时，按原幂等键恢复已提交结果。

## Q-007：数据冲突和回滚

建议不覆盖审批期间或发布后发生的其他修改；回滚产生新的反向发布单，也需要他人审批。

- 例如原单基于值 1，希望改为 2；审批等待期间原记录或其并发版本变化，发布被拒绝，业务数据和全部变更记录都不改变。界面保留申请内容，支持查看最新值、取消旧单并重建。
- 单据提交后，表结构或实际变更规则变化时拒绝执行，要求重新确认并建单；显示名称或描述变化不属于执行语义变化。停用表规则或撤销当前操作者角色立即阻止后续操作。
- 普通读取操作不会改动业务表；记录版本放在平台控制表，删除后重建同 id 不能让旧请求重新有效。不能只对比字段值来替代记录版本。
- 已发布单提供“申请回滚”，生成有关联的新草稿。反向内容恢复原单影响的业务字段，使用原发布结果作为基线；生成列、默认值、数据库约束和当前自动审计规则仍由真实执行校验。
- 原单把 1 改成 2，后续发布又改成 3，此时回滚原单会被拒绝，不能把 3 强制改回 1。首版无强制覆盖或强制回滚按钮。
- 反向单完成审批及发布后，原单显示已回滚，反向变更推进新的记录版本和表版本，并产生新的 Command、日志和通知记录。保留全部历史，不删除原发布结果。
- 若原数据已不满足当前约束，例如恢复已删除记录违反新的唯一约束，整单回滚发布失败且零副作用，说明冲突；不绕过数据库约束。

## Q-008：账号角色与存量切换

建议角色可组合，新增和存量账号切换后默认只读。部署维护者使用已有账号维护命令，为明确指定的账号首次授予 ADMIN；其后由管理台的账号角色页面分配角色。注册先后顺序不授予管理权。

| 角色 | 能力 |
|---|---|
| VIEWER | 查看配置记录、发布单、变更差异和发布历史 |
| EDITOR | 包含查看能力；创建、修改和提交自己的草稿，申请回滚，按规则取消自己的单据 |
| APPROVER | 包含查看能力；批准/拒绝其他人提交的单据 |
| PUBLISHER | 包含查看能力；执行已批准单据 |
| ADMIN | 管理账号角色和规则目录，拥有上述业务能力及取消异常单据的能力，仍不能自批 |

- 规则目录仍直接保存和管理，不进入发布单审批，但管理权限收敛到 ADMIN。其他角色可以读取解释配置记录行为所必需的有效规则，不能修改规则。
- 角色调整立即约束下一次服务端请求，不依赖退出重登。角色变更记录永久操作者、对象和前后角色。
- 不允许通过管理界面撤销或停用最后一个启用的 ADMIN；维护命令提供可审计的恢复方式。
- 已经合法作出的审批保留为历史事实，不因为审批人后来角色变化被自动改写；执行者必须在执行当时仍有权限。需撤销发布意图时显式取消。
- 迁移使用维护窗口：先准备角色与发布控制数据，指定首位管理员，升级调用方并关闭直写入口，再恢复服务。无法确认角色目录有效时拒绝业务操作，不默认为全员有权。

## 已确认范围必须满足的失败语义与验证建议

以下不额外扩大业务范围，用于后续规格综合与验收确认：

- 网络超时、重复点击和提交响应丢失时，同一幂等键只能关联一个结果。界面保留输入和幂等键，提供查询或原键重试；修改内容后必须成为新的明确操作。不得静默重试为新请求。
- 任意明细校验、约束、版本、最终行读取、Command/版本/日志/Outbox 持久化失败，整次事务回滚。数据库不可用时不展示“已发布”；进程在提交后退出也不能丢失持久化结果。
- 审计保留申请、提交、审批、执行、取消、回滚和角色调整的稳定身份及原因。完整配置差异仅在授权详情中显示，不写普通应用日志或错误响应；不删除历史。
- 审批历史、发布单状态版本、配置记录并发版本、表发布版本各自有明确用途，不混成同一个“版本”。
- 主要验收从真实登录身份调用 Admin HTTP API，观察状态、权限、返回的差异与实际查询结果；真实 MySQL 验证事务、唯一性、并发、默认值/生成列/触发器后的最终行。
- 浏览器覆盖“编辑 → 草稿 → 另一账号审批 → 发布 → 查询新值 → 申请回滚 → 审批 → 恢复”的完整路径，以及权限禁用、冲突保留输入和刷新后的状态恢复。复用已有测试与 UI，不为这些已可明确描述的规则另造原型。
- 最终规格将为上述承诺分配稳定的 AC 编号，再以各工单独立交付的行为分配验证证据。持久化通知记录可验收，实际通知投递与消费者收敛不属于本期完成承诺。

## 已核实的实现与协议边界

- 现有账号维护程序能够按永久 Account ID 或用户名查找账号，并拥有独立于 Web 登录的数据库维护入口，可扩展首次授予 ADMIN；现有程序尚无角色命令，Web 也没有账号列表/角色管理页面，二者都需要真实交付。
- 当前会话每个请求重新校验账号状态，可在业务操作中按永久 Account ID 读取当前角色。已有“会话撤销不终止已认证在途请求”的承诺继续适用；本期角色立即生效指后续请求，不能暗示撤销会杀掉已经提交的事务。
- 现有浏览器系统验收覆盖真实 Admin 与 MySQL，但其“注册后直接写数据”流程需要随本功能迁移。现有 `make test-browser` 只匹配账号验收函数，新增发布单关键路径时必须扩展运行入口，防止新用例未被执行。
- Command、表版本与规范编码目前只有候选文档，没有可直接调用的实现。Admin 的 SQL NULL 与 Server 候选字符串编码存在差别，本期必须定义有版本的无损持久化编码，不能直接把现有 HTTP JSON 当作可信最终行。
- 本期 Command 绑定当前单个 Managed Data Source 和表，使用显式协议版本，不伪造 `environment=production`，不声称已经符合未来多环境 Server 协议。未来 Environment 与 Runtime 接入时必须有正式迁移/转换方案和真实联调，原始持久化记录保持可追溯。
- 记录并发版本、表变更次数和 Command 游标分别维护。未来版本大盘的 MD5、`source_updated_at` 等字段不在本期虚构，也不能用本地执行时间或另一个摘要冒充。
- 支持范围需覆盖数据库默认值、生成列和目标行的实际最终值；触发器、级联或其他隐式写入若导致无法列举的额外受管行变化，必须在业务写入前拒绝该表的发布。不能只记录显式目标行后声称所有附带变更都有 Command。

## 明确非目标

环境隔离、Page Model、跨表发布、配置 Schema 编辑、规则目录审批、灰度、模板设计器、多级或应急审批、定时发布、批量文件导入、强制覆盖、Server/Client 实际分发、通知投递 worker、死信重放和版本大盘均不进入本期。历史行和发布记录的自动清理不在本期实现。
