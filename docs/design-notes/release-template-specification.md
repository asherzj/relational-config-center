- **B-004：区分节点实例与审批安排。** 节点定义在展示前持久化，之后不被模板修改或停用替换；常规的表审批角色分配按 #92 在提交时固定、成员资格实时。草稿显示的审批安排明确为提交前安排，不能把它显示成已经冻结的人员承诺。提交不更换节点实例；业务内容和执行语义仍按正式提交能力冻结。

## 问题陈述

发布流程目前由固定逻辑决定，管理员无法用可复用配置为不同表设置常规与应急流程；应急发布需要免审批但仍受当前权限、整单事务和恢复保护约束。用户看到流程后需要保留这份实例，不应因共享模板后续修改而被换成另一条流程。

## 解决方案

管理员在正式管理页面维护两类模板及表关联。同类型允许多个模板，每张表每类型关联一个模板；应急模板与关联始终有效，常规可停用。模板继续以 node_list 保存完整有序节点，仅允许常规的审批、发布、完结和应急的发布、完结两种组合。

申请人为整单选择发布方式。展示流程前各表创建独立节点实例；草稿切换方式才整体重新实例化，通常编辑保持已有实例。常规提交进入正式按表审批，应急提交记录原因并进入待发布，由当前发布人员手动执行。发布、占用、结果、通知、完结和原单回滚复用现有业务能力。

## 故障与一致性决策

1. 模板或关联明确缺失与存储读取失败分别报告；读取失败不能伪装无配置、无审批资格或自动选择一份内置流程。“应急始终可用”是系统配置约束，不意味着数据库故障、撤权或业务冲突时继续发布。
2. 模板和关联编辑各自保护可观察版本。实例化须一致读取模板及关联；管理员竞争、草稿改方式与提交竞争不能形成混合实例或覆盖旧编辑。流程字段、实例、草稿版本及相关明细操作一起成功或保持原状态。
3. 同请求重推复用身份及内容，已提交返回原结果，未提交可按当前授权执行；不同内容复用同键拒绝。重推已成功的实例化不得因模板更新生成另一份实例。
4. 超时或响应丢失不等于未提交。沿用 #81/#92 的原操作手动重推，无自动业务重试或独立结果确认流程；界面保留输入与原请求，跨账号不重放。
5. 多表执行维持 #81 的顺序、一次事务、版本、占用和结果约束。应急免审批不豁免记录冲突、结构与规则执行语义变化、业务约束或当前角色检查。
6. 当应急模板或关联更新使其非法或不可用时，操作拒绝且原配置保持有效；创建/启用受管表与有效应急关联不能部分成功。切换关联不得先解除保护再补绑。
7. 站内通知采用 #92 的真实业务事实；应急不创建审批待办。成功状态及结果通知一致提交，通知读取失败不倒推发布失败；刷新通知记录不意味着消费者已接收。
8. 原单回滚仍只允许待完结阶段，业务恢复基线在真实执行时再核对；提前保存应急节点实例不冻结业务当前值，也不延长回滚时限。
9. 结构升级采用 Goose 的向前迁移与显式恢复。DDL 不承诺事务回滚；迁移失败必须被正式就绪检查识别，不将应用事务承诺套用于 DDL。没有旧发布单数据兼容，不自动清理用户数据。
10. 灰度、外部监控、跨库和外部推送不属于本期，省略相关未来故障场景与补偿机制。

## 实现决策

- 新增发布流程模板定义、表与模板关联两张配置表；两张表独立于 #81 已有主单、明细、执行记录三类业务表。实例存储扩展现有发布单体系，不增加第三张配置表或独立回滚业务表。
- 定义包含稳定唯一编码、名称、发布类型、有序节点列表、描述、启用状态、操作者、时间及编辑并发版本；同类型可有多个模板。关联包含表规则身份、发布类型、模板身份、启用状态、审计及并发版本，每表每类型唯一且类型必须匹配。
- 模板编码和类型作为稳定身份属性；节点类型来自预定义能力。管理表单根据类型给出合法组合，允许配置名称及合法参数，不提供任意脚本、SQL、重排、多级审批或自定义执行节点。
- 审批节点复用表审批能力，不存另一份角色成员分配。发布/完结仍检查全局动作权限及每个适用实例的有效限制；多表不能挑权限最宽的一份模板绕过其他约束。ADMIN 的全局权限含义沿用正式账号能力，禁止自审仍单独执行。
- 初始化默认常规、应急模板各一份，身份稳定；已有表显式关联默认值，新表成为受管表时确保有效应急关联，常规关联由管理员选择。重跑不得覆盖管理员已配置的有效关联。
- 应急模板不可通过禁用、删除或无效编辑失效；应急关联不能禁用、解绑或指向错误类型。常规模板可停用；删除被关联对象不得造成悬空引用。首期不需要增加一套模板发布审批或多版本激活生命周期。
- 实例化是显式保存行为，成功后才展示节点；普通详情读取不得悄悄产生新实例。新增表、改选方式、复制/重新准备采用受控写入；常规配置恢复后，用户再次保存草稿只补齐尚缺的流程实例；旧实例的名称、节点及参数不被源模板覆盖。
- 多表的流程实例按表可审阅，整单阶段显示一致的业务含义；不会把无审批应急写成已批准，也不在原单回滚中补造审批或人工完结事件。
- 管理目录使用现有列表、抽屉、选择器、错误与焦点组件；模板管理置于表配置管理，表关联在表设置维护。发布单增加类型及各表实例展示，应急正向原因输入靠近提交动作。移动端按现有单列与局部滚动规则适配。
- 复用正式公共 API、错误码模式、会话恢复和安全重推；新增控制表只能由专用管理能力操作，不能通过通用配置记录入口管理自身。
- 实现以已合并的多表和 Goose 基线为基础；常规审批接入须等按表审批交付提交可用，通知接入须等结果提醒能力可用。不能从本任务旧 checkout 重新建一套单表或全局审批路径。

## 测试决策

- AC-001～AC-027 均需可重复证据。HTTP 与真实 MySQL 是授权、关系、实例隔离、事务、幂等及竞争的主要证据；不为每个私有函数添加与实现同形的测试。
- 模块测试仅独立证明节点组合和权限参数校验等局部规则；高层重复实例、停用影响和发布状态以公开契约验收，不逐层重复相同事实。
- 使用现有真实应用与 MySQL 集成先例；并发两个管理员、两份草稿编辑、模板切换与实例化、已提交丢响应及重复请求均覆盖真实提交边界。故障注入作用于真实依赖，不以模拟自有仓库接口代替事务证据。
- 浏览器证明 ADMIN 建模板→表关联→多表草稿实例→常规/应急提交→手动发布→完结或原单回滚→结果/通知跳转；桌面与 390px、键盘、长值、会话失效和错误输入保护纳入切片自身验收。
- 各切片只运行自身必要检查和受影响回归；T6 统一负责完整集成验收与 AC 证据索引，已有依赖证据只有在相关代码及契约未变化时才复用。
- 迁移验证通过正式维护命令、真实新建与升级结构及 Admin 就绪检查；旧独立回滚、全局 APPROVER 旁路和固定节点兜底退出由公共契约及结构/依赖检查证明。
- 每个实现工单按其稳定基点和父规格做 Standards/Spec 双轴评审；最终同步设计基准与真实页面，不用修改验收标准掩盖差异。

## 临时结构与退出条件

最终不保留旧固定流程兜底、双写或旧发布单数据兼容层。切片 T1/T2 只交付配置管理，T3 接通常规实例，T4 接通应急，T5 接入原单回滚与通知；中间阶段尚未接通的能力不宣称可执行。
