# T2：校验并接管当前存量数据库

## 父工单

Part of #67：https://github.com/asherzj/relational-config-center/issues/67

状态：用户已确认，ready-for-agent。

## 要构建什么

维护者可以显式接管符合冻结基线的存量库，接管前完整比较物理结构和必要控制元数据，成功后由 Goose 管理后续升级。已有账号、会话、规则、记录版本及发布历史保留；不兼容库明确拒绝，更旧的库按历史流程到达基线后才接管。

## 验收标准

- [ ] AC-004：真实存量库经完整校验登记基线，重复接管返回已接管结果；已有业务/控制数据、管理员授权和历史保留。
- [ ] AC-005：代表性的缺表、缺列、不兼容额外列、类型/默认值/索引/CHECK/引擎差异和必要元数据缺失均明确拒绝；不能用可 SELECT 代替结构验证。
- [ ] AC-006：历史库首先被拒绝并获得操作指引，按既有维护流程升级后可接管；不把一次性旧脚本改写为可整体重放历史。
- [ ] 基线接管和重复接管复用 T1 的互斥与持久状态，不允许普通升级绕过接管检查。
- [ ] 新安装和接管使用相同的当前结构要求，但测试以独立结构预期和固定数据验收，避免实现自证。

## 验收用例

主要交付 AC-004、AC-005、AC-006。完整 Given/When/Then 沿用父规格；接管时的竞争和中断场景验证其正确接入 T1 的承诺，不另建一套平行状态机。

## 验证证据

真实 MySQL 控制结构差异验证接管拒绝；固定账号、会话、规则、发布和记录版本数据证明保留。代表性旧库通过现有 Policy 维护命令及历史 SQL 到达基线，再以公开命令接管；现有账号/发布读取回归证明业务仍可用。运行本工单相关与完整必要检查并评审。

## 临时结构与退出条件

无新临时兼容层。历史脚本和维护命令保留明确旧库职责；T1 的旧当前初始化入口仍由 T3 统一删除，不在此引入静默接管、跳过校验或自动降级开关。
