## 已核实的实现基础

- 已有独立详情地址 `/configuration/release-orders/:id`，与列表复用 `ReleaseOrdersPage`，无需为截图重复建立详情入口。

- 当前历史直接展示完整记录，尚未整理成中文时间线和最近记录摘要。

## 展示信息范围（第三轮已确认）

1. **发布单标题**：新增由申请人填写的标题，补创建/编辑、持久化和读取契约；草稿可编辑，提交后冻结。
2. **单号**：保留现有真实 ID，补复制与完整查看，不新增 REL 日期流水编号。
3. **人员姓名**：显示当前姓名，永久 Account ID 保留用于归属及无法解析时兜底；采用姓名首字头像。本地账号已有显示名，但查询其他账号的列表仅允许 ADMIN，需要提供普通查看者可用的人员展示数据。
4. **明细与字段**：明细使用操作类型和记录 ID，字段显示真实英文字段名。本期不建设通用业务记录标题和字段中文标签配置。

人员展示仍须遵守 [ADR-0018](../adr/0018-attribute-authored-changes-to-stable-account-ids.md)：历史归属使用永久账号标识，显示名不能代替身份。

## 已有业务边界对截图的约束

- **重新准备**：APPROVED 只允许 execute/cancel，只有 DRAFT 可编辑，只有普通 REJECTED/CANCELLED 单可复制。取消后核对当前记录并复制为新草稿可以组合已有能力，但取消与复制不是同一事务，必须处理取消成功而复制未完成的情况。原单退回修改则是新增流程。
- **审批内容**：修改获批内容后沿用旧审批与 [ADR-0020](../adr/0020-reapprove-rollback-and-reject-stale-publications.md) 冲突；新增任何返回编辑路径都必须明确重新审批。
- **完结**：SUCCEEDED 表示整单数据库事务提交成功，没有单独完结动作；通知为 NOT_CONNECTED。根据 [ADR-0019](../adr/0019-require-release-orders-for-managed-record-changes.md)，本期尚无 Server/Client 实际分发，步骤条不能表示消费者已生效。
- **变更后**：发布前是申请值，自动审计字段、默认值和生成列的最终结果可能尚未确定；发布后真实结果应取 publication 数据。
- **仅看变更**：不能只比较字符串；未提交、SQL NULL、空字符串、不存在、自动填写、数据库生成具有不同含义。
- **版本**：截图中的版本应明确为“发布单版本”，不可与记录并发版本或表发布版本混用。
- **视觉与外壳**：[Web 设计规范](../../web/DESIGN.md) 当前采用中性灰与石墨色主按钮，D-001 已确认沿用现有全站外观。单数据源目前是静态说明，没有切换能力。

## 第一轮已确认决定

### D-001 / Q1：页面范围

用户同意：聚焦发布单详情，覆盖全部现有状态，并保留列表进入/返回、关联单跳转和必要的草稿入口衔接。全站外观沿用现有规范。

### D-002 / Q2：重新准备

用户同意：保留原单历史，取消原单后核对当前数据、复制成新草稿，修改后重新提交审批。不能修改获批内容后继续使用原审批。

权限与失败结果按 D-014/D-015 落实：新申请人是实际操作者，取消旧单与生成新草稿共同成功或共同失败。反向发布单沿用既有固定内容与重新申请边界。

### D-003 / Q3：发布成功不自动完结

用户明确纠正原建议：“最后一个完结节点用于给发布人快速回滚用，所以配置发布成功之后不自动完结”。

已确认发布成功与发布单完结是不同业务事实。发布成功后需要保留用于快速回滚的阶段，不能直接将最后一步显示为已完成。`admin/CONTEXT.md` 已记录这个概念区别。

随后通过 D-004～D-007 确认免再次审批、当前权限授权、人工完结及继续占用，D-008/D-016 明确两类回滚成功后均直接结束。

## 发布后阶段的代码核实

- 当前回滚由 EDITOR 创建反向草稿，再由申请人提交、另一位 APPROVER 审批、PUBLISHER 执行；并无发布人直接回滚接口。见 [回滚说明](../admin-release-rollbacks.md)及 [Rollback](../../admin/internal/application/rollback.go)。
- 当前成功执行在同一事务内立即释放在途目标，见 [publication.go](../../admin/internal/application/publication.go)。仅增加未完结显示不会保留回滚机会。
- 例：A 单将 #1024 优先级从 100 发布为 200，产生记录版本 8。随后 B 单可以提交并占用 #1024；如果 B 再发布为 300、版本变为 9，A 的回滚会拒绝。B 只修改这条记录的其他字段也会推进记录版本。
- 若 B 仅提交尚未发布，A 回滚可能在取得在途目标时被阻止；B 只修改同表另一条记录则不会仅因同表有更新而阻止 A 回滚。
- 用户现已确认这两项改变，见 [ADR-0023](../adr/0023-keep-published-orders-open-for-quick-rollback.md)。ADR-0019/0020/0022 已增加部分调整说明，明确区分新决定与仍在运行的原实现。

## 第二轮已确认决定

### D-004 / Q4：快速回滚免再次审批

用户回复“不需要”：待完结期间的快速回滚无需再次审批。整单恢复、历史保留和禁止覆盖后续修改的原有边界保持；不把免审批实现为伪造 APPROVE 事件或自动以申请人身份批准。

### D-005 / Q5：按当前权限开放

用户明确修正：“只要有权限的，都可以操作。”快速回滚和完结不限定原发布人，按当前发布权限开放，沿用现有 PUBLISHER/ADMIN 授权能力；实际操作者独立记录。

### D-006 / Q6：人工完结关闭快速回滚

用户同意：由人明确点击确认完结，不自动倒计时；完结后关闭快速回滚入口，需要恢复时走现有重新审批的回滚流程，不重新打开原单。

### D-007 / Q7：占用保留到完结或回滚成功

用户同意：继续占用本单涉及的记录，直到完结或回滚成功，阻止其他发布单在此期间修改同一批记录。同表其他记录可以继续发布；数据库外部改动及规则变化仍须检查，不能承诺无条件回滚。

由上述规则直接得出：明确回滚失败不应冒充成功，也不应自动释放占用或完结。未知结果须沿用原请求恢复，不能凭超时认定事务失败并放开互斥操作。

## 新规则的实现约束（代码调研事实）

- 自增 ADD 在提交时尚无实际 ID，没有在途目标；执行后实际身份保存在发布结果中。因此必须在成功事务中补齐真实新增记录的占用，仅取消 ReleaseTargets 调用不够。
- DELETE 也要继续占用删除后的记录身份，避免其他单在快速回滚前重新新增同 ID；已有墓碑身份可复用。
- 原单持有的目标会使普通反向单的提交及执行都报冲突。快速回滚需要在事务内协调已有占用和反向写入，不能先释放再尝试回滚，也不能把原单占用视为任意账号可忽略的冲突。
- 用户已说明没有旧发布单数据，先前对历史成功单、旧在途回滚申请和旧发布请求快照的迁移分析不再构成本次需求。新功能自身的请求恢复与当前状态刷新仍须验证。

依据：[发布执行及实际身份](../../admin/internal/infrastructure/mysql/publication.go)、[执行时占用检查](../../admin/internal/infrastructure/mysql/publication_versions.go)、[目标存储与原请求结果](../../admin/internal/infrastructure/mysql/release_orders.go)、[原单与反向单关联](../../admin/internal/application/rollback.go)。未查询实际部署中的历史单数量或数据状态。

## 第四轮已确认决定

### D-014 / Q14：重新准备的权限与新申请人

用户同意。普通已批准但未发布的单据提供“重新准备”：申请人本人仍有编辑权限时可操作，ADMIN 也可操作；新草稿申请人是实际重新准备的人，仍禁止审批自己的新单。Q5 的放宽仅针对快速回滚与完结，不扩大为任意 PUBLISHER 可重新准备他人申请。

### D-015 / Q15：重新准备共同成功或失败

用户同意。先展示按当前数据核实的差异，由用户明确确认后，将原单取消和新草稿创建作为同一次业务操作完成。成功则原单已取消且新草稿已生成；明确失败则原单的审批和占用保持原状。响应丢失时使用原请求找回同一个结果。

这仍遵循 D-002 的取消旧单、创建新草稿、重新审批路径，但需要新增协调后的后端操作，不能直接先后调用现有两个独立写接口。当前 cancel 只允许有权限的申请人或 ADMIN，copy 的新申请人为实际复制人；复制会重验记录与规则，后一步确实可能失败。

### D-016 / Q16：所有回滚成功均直接结束

用户同意。快速回滚和完结后通过审批执行的普通回滚，都在成功后结束并释放占用；回滚结果不再进入待完结，也不再提供对回滚结果继续反向回滚的入口。需要重新发布时走新建普通发布单和审批。

当前普通反向单成功后自身仍为 SUCCEEDED，现有状态判断还允许它申请下一次回滚；因此不能仅给所有 SUCCEEDED 单统一增加待完结交互。

### D-017 / Q17：页面默认交互

用户同意本组页面行为，落实如下：

- 标题必填，最多 100 个 Unicode 字符；创建草稿时预填“表名 配置变更”，草稿可改，提交后冻结。复制保留原标题供新申请人修改，审批回滚标题由来源标题生成并展示。
- 初次打开默认“仅看变更”并展开第一项；每页保留 20 项。MODIFY 隐藏确定不变的字段，自动填写或数据库生成的字段保留待生成说明；ADD/DELETE 展示整条记录。NULL、空字符串、未提交、记录不存在不混为同一种值。
- 发布前显示“原值／申请值”；发布成功后默认展示实际发布结果，同时可切回申请差异。回滚后醒目显示已回滚并提供真实回滚结果与原发布结果入口。
- 操作历史最近 5 条倒序显示，支持展开全部。步骤区根据真实提交、审批、发布及完结事件显示人员时间；准备完成取提交时间。
- 快速回滚先查看恢复差异、填写必填原因，再确认执行。完结二次确认说明会释放占用并关闭快速回滚，不强制填写额外意见。步骤条用于进度展示，不通过点击跳过业务步骤。

失败保持原状态、并发动作至多一个成功、网络未知结果保留原请求恢复、权限实时检查等沿用已有业务保证及 D-004～D-007。文档定稿不表示功能已经实现或通过运行验收。
