# 规格：多表发布单、草稿目标占用与统一执行

状态：用户已确认验收接缝、AC-001～AC-015和非目标；规格与七张切片已确认并发布；T1～T6 已本地交付，T7 实现与[本地最终验收](../verification/2026-09-11-feature-81-acceptance-index.md)已完成，尚未合并或部署。仅采用本次最新方案及Q1–Q22，不沿用已清空的旧规格或工单拆分。

## 问题陈述

配置变更需要跨多张表组织成一张发布单，在草稿准备期间即保护将要变更或恢复的业务目标，避免多人准备互相冲突的配置。发布与应急回滚需要共享真实执行逻辑，同时保留原始申请和两次实际结果，减少独立回滚单和重复数据结构。

## 解决方案

一张发布单管理多表、最多1000条有序明细。草稿保存时按主键及表规则中的并发管控键原子取得占用，以整单版本保护分页编辑。发布和回滚使用同一执行器，在同一数据源内以整单一个事务执行。发布成功保留待完结及占用；未完结时可预览后一次确认免审批倒序回滚，回滚成功终止原单并释放占用。已完结或已回滚单不能回滚。

主单、变更明细和成功执行记录分别存储，不再创建独立回滚发布单，不建立执行结果明细表。异常由前端报错，不自动重试或增加独立结果确认流程；用户可重推原操作，后端以事务和幂等保证不会部分生效或重复生效。

## 用户故事

1. 作为编辑者，我想将多张表的新增、修改和删除放在同一发布单，以便一起审批和生效。
2. 作为编辑者，我想保存明细时即取得目标占用，以免其他发布单准备相同目标。
3. 作为编辑者，我想看到占用单号和负责人，以便协调冲突。
4. 作为编辑者，我想分页添加、编辑、删除和调整明细顺序，以便处理较大的变更。
5. 作为编辑者，我想并发编辑时保留输入并拒绝覆盖，以免丢失他人的修改。
6. 作为管理员，我想按真实字段定义单字段或组合并发管控键，以便保护业务身份。
7. 作为管理员，我想在未结束单引用表时阻止管控键定义变化，以免旧草稿失去保护。
8. 作为管理员，我想取消遗留草稿释放占用，以便处理无人维护的工作。
9. 作为编辑者，我想复制已拒绝或取消的单时重新竞争占用，以便按当前数据重新开始。
10. 作为原申请人或管理员，我想重新准备已批准未发布的单时原子转移占用，以免保护出现空隙。
11. 作为审批人，我想审阅冻结的完整多表明细和顺序，以便知道批准的准确内容。
12. 作为发布人员，我想所有明细按冻结顺序一次提交，以免只发布一部分。
13. 作为发布人员，我想在待完结期间预览恢复差异并一次确认整单回滚，以便应急恢复。
14. 作为查看者，我想在原单区分申请、实际发布和实际回滚结果，以便追溯事实。
15. 作为回滚执行人或管理员，我想事后选填或修正原因并留痕，以便不延误应急处理。
16. 作为操作人，我想请求异常时得到真实错误，并能安全重推原操作，以免重复执行或被额外确认流程阻挡。
17. 作为维护者，我想升级表结构并移除旧回滚单路径，以便维护统一的实现。

## 验收接缝

主接缝为正式Web的表规则配置、发布单列表/详情、多表草稿编辑及审批/发布/回滚操作。辅助接缝为已认证Admin公开HTTP API和真实MySQL，独立证明规则与占用原子性、多表事务、权限、版本及幂等。浏览器覆盖桌面和390px、分页、键盘、长值、错误和原操作重推，不新增测试专用业务入口。

## 故障与一致性决策

- 仅在当前部署的同一Managed Data Source内支持多表，一个整单操作一个事务；不引入跨库补偿或拆事务执行。
- 草稿保存、删除和重排使用整单版本；明细变更与占用更新原子提交，失败保持已保存内容和保护。管控键定义修改与未结束单引用登记必须互斥，不能只先查再写。
- 新增保护新值、修改旧新值、删除旧值；占用保护不是唯一约束替代，发布仍检查实际值、记录版本、结构、规则、唯一约束及外键。外部SQL和结构变化不得被静默覆盖。
- 发布正序、回滚倒序，提交后冻结；同表同主键只允许一条，不支持同ID先删后增或自动重排来绕过约束。
- 业务数据、相关表/记录版本、实际结果、成功执行记录、主单、目标及刷新通知一起提交；刷新通知不等于下游已接收。
- 所有相关写接口维持当前权限、账号隔离、事务和幂等。同一业务请求重推复用幂等身份，已提交返回原结果，未提交允许执行，同键异内容拒绝。当前权限和整单版本不得被重推绕过。
- 前端明确报错，不自动重试；没有独立的结果确认按钮或确认流程。超时不证明后台未提交，主单状态通过正常读取获得；用户可重新点击原操作，后端幂等保证不重复生效。
- 已确认未提交的失败可以另行记录失败历史，失败审计不得使业务部分提交；数据库不可用时允许明确告知失败历史未保存。未知提交结果不得伪装为确定失败。
- 原因修改不改变执行事实，使用真实操作者及时间留痕；其写入仍遵守权限、事务和幂等。

## 实现决策

- 三类业务表分离主单流程、变更明细、整单成功执行。每条明细包含原始申请与两次实际结果；执行记录只存整单摘要及明细关联，不重新嵌入全部明细，不创建执行结果明细表。
- 业务明细明确所属表和整单顺序；列表只显示主单，详情提供多表明细分页及三种内容的审阅。
- 表规则增加零组或一组管控键定义；主键占用保留，新增类型支持必须依据真实字段比较语义，不通过字符串简单拼接代替等价规则。
- 草稿期取得占用，未结束单对表的引用也阻止管控键定义变化；管理遗留草稿采用取消，不设置自动到期。
- 沿用现有后端执行器，改造多表计划和结果归属；锁定顺序可由实现保证竞争安全，但不得改变已冻结的业务执行顺序。
- 沿用当前Web设计组件与权限体系。新增多表选择、分页编辑与排序、管控键设置、原单结果展示和原因补填，保留可访问性及输入保护。
- 仅保留本次确认的1000条上限，不采用Q20提出的固定字节上限；相关旧链路限制必须同步调整，不变更无关功能。
- 不设计旧发布单数据兼容；保留结构升级能力，不将此决定当作删除环境数据授权。
- 本次没有必须依赖运行或视觉原型才能决定的问题；实现阶段需真实浏览器验收。
