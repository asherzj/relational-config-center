## 已核实的实现基础

- main 已有本地账号、Cookie 登录会话、CSRF 保护和永久 Account ID。沿用现有身份机制；候选发布规格中的可信代理身份头条款已被 ADR-0017 取代。

- 数据页的 Change Set 仅是前端字段差异预览；确认后直接调用单行 ADD/MODIFY/DELETE API。
- 单行写入已有规则快照、实时 Schema、自动字段、真实操作人和 MySQL 事务。尚无发布单、审批、模板、目标占位、写请求幂等、Command、发布版本或 Outbox。
- 当前配置内容来自部署指定的单个 MySQL database，以受管表和 id 定位。没有已交付的环境隔离或 Page Model。
- GitHub #33 已确认独立控制表维护配置记录的 `lock_version`、同事务比较和推进、删除重建不能使旧版本重新有效。该需求尚未实现；发布单自身的状态版本不能替代配置记录并发版本。
- Server 和 Client 仍为骨架。

## 第三轮已确认决定

用户要求将问题直接集中列在回复中，不使用 Codex 交互卡片；其后对四个编号问题分别回复“同意”。后续需要确认的内容继续集中用普通回复呈现。

### D-005：单表混合批量

一张单对应一张受管表，支持 1～1,000 项 ADD/MODIFY/DELETE，全部成功或全部失败。管理台支持将变更加入草稿和批量删除，不做文件导入。已知 id 防重复占用；省略自增 id 的新增以请求幂等和数据库唯一约束防重，不猜测业务字段含义。

### D-006：固定单人审批流程

草稿 → 提交 → 一人审批 → 手动发布。提交后内容冻结，拒绝后复制为新草稿重新申请；发布前申请人或管理员可取消。审批人与发布人可相同；申请人若有发布权限，可以执行别人已批准的自己的单据。

### D-007：冲突拒绝，回滚重新审批

审批期间数据、表结构或变更规则变化时拒绝发布，保留原申请供重新确认。回滚生成新的反向发布单，也需要他人审批；原单发布后数据又被修改时，不允许回滚覆盖后续修改。

### D-008：账号默认只读，由管理员分配角色

新增和存量账号默认只读，由部署维护命令指定首位管理员，再通过管理台分配可组合角色。只有管理员能修改角色和规则目录；角色调整对后续请求立即生效；管理员仍不能自批。

用户随后回复“按推荐”，确认以下八项，依次编号 D-009～D-016：

1. **D-009：全局角色。**角色覆盖当前单库内所有受管表，首版不按表、部门或人员组授权。
2. **D-010：合法审批保留。**审批人后来停用或失去角色不使原审批自动失效；新动作实时校验权限，需要撤回时显式取消。
3. **D-011：占用从提交到结束。**草稿不占用，提交后占用，拒绝/取消/发布成功释放；失败仍占用，无自动到期释放。
4. **D-012：实际执行人归因。**业务表自动操作人字段写实际执行人 C；发布单完整保留申请人 A、审批人 B 和执行人 C。
5. **D-013：回滚业务值而非旧审计字段。**自动操作人/时间记录本次回滚，生成列重新计算，违反当前约束整体拒绝。
6. **D-014：明确失败与结果未知。**明确回滚保持已批准可重试，未知结果保留原键查询/重试；成功仅表示数据库业务和相关记录共同提交。
7. **D-015：附带写入完整追踪。**触发器/级联导致额外记录变化而无法完整追踪时，在业务写入前明确拒绝该表，不能遗漏变更却报告成功。
8. **D-016：长期保留历史。**发布、审批、差异和操作历史不自动清理，废弃草稿取消归档而非物理删除。
