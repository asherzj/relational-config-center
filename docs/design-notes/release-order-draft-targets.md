# 发布单明细、草稿目标占用与统一执行

状态：方案与验收已确认，规格已发布为 #81，尚未实现。用户要求清空此前本轮方案及澄清；本文件仅以2026-09-09最新输入为依据，旧问答、验收编号与工单拆分不沿用。

## 方案

一张发布单管理来自多张业务表的 N 条变更明细，从草稿保存时占用目标记录，发布和回滚共用执行逻辑。

## 数据结构

| 表 | 保存内容 |
| --- | --- |
| 发布单主表 | 标题、申请人、审批、生命周期状态、整单版本 |
| 发布单变更明细表 | N 条新增／修改／删除意图、before/after、实际发布结果、实际回滚结果；三者分别保存且互不覆盖 |
| 发布执行记录表 | 执行类型、执行人、时间、版本及整单结果；最多两条成功记录：发布、回滚 |

不创建独立回滚发布单，不建立执行结果明细表；列表只展示主单。

## 草稿与并发

- 空单不占用记录；明细保存进草稿时取得对应目标占用，其他单不能保存涉及同一目标的变更。
- 保存明细与取得占用在同一事务完成；删除明细时释放对应占用。
- 编辑采用整单版本控制：事务内锁主单、检查草稿状态和版本、更新明细并增加版本。冲突时拒绝覆盖、保留用户输入。
- 提交审批后冻结明细，占用持续保留到取消、拒绝、完结或回滚成功。
- 显示占用单号和负责人；管理员可取消遗留草稿，不自动过期释放。
- 自增 ID 的新增记录在发布后占用实际 ID；唯一键冲突仍需检查。

## 发布与回滚

- 正向发布与逆向回滚共用执行器。
- 每次整单操作使用一个事务：业务数据、版本、执行记录、主单状态和占用一起提交，失败全部撤销。
- 发布成功后保持待完结，继续占用目标。
- 当前有发布权限的人可在原单查看恢复差异，一次确认整单回滚，无需审批；原因可事后选填并留痕。
- 回滚成功后原单结束并释放占用；已完结单禁止回滚，也不能再次回滚已回滚单。
- 保留一致性检查、幂等重试和未知结果恢复，避免部分恢复或重复执行。

## 范围与未决项

明细支持分页，但分页不改变整单事务要求；已确认多表合计最多1000条。本次不做旧数据兼容。此约定不授权清理现有环境数据。


## 本方案澄清记录

### Q1：明细与执行结果（已确认）

每条变更明细分别保存原始申请、实际发布结果、实际回滚结果，互不覆盖。执行记录保存整单摘要并关联这些明细，不再次在整单JSON内复制全部明细。

### Q2：并发管控键（用户提出的新规则）

- 表规则定义“并发管控键”，支持单字段或字段组合，例如 `[tenant_id, channel_code]`。占用目标由表及键值组成，例如渠道表的 `(42, wechat)`。
- 主键占用始终保留，管控键作为补充；不同发布单涉及同一目标时后保存请求被拒绝，显示占用单号与负责人。
- 新增占用新值，修改保护旧值和新值，删除保护旧值，为回滚保留空间。
- 草稿明细保存和占用取得在同一事务内更新；删除草稿明细时只释放不再需要的占用。
- 提交、审批、发布后持续保留占用，到取消、拒绝、完结或回滚成功释放。
- 配置引用真实字段，键值须在草稿保存时能确定。有在途占用时禁止改变管控键定义。
- 不自动占用所有数据库唯一键；发布时仍检查唯一约束和数据一致性。
- 整单版本控制负责同一单的编辑冲突；管控键负责不同单的冲突，不能互相替代。

该方案调整现有“提交审批时才取得主键占用”的边界，并扩展表规则职责；实现仍为原行为，后续规格与ADR需准确表达这些变化。


### Q3–Q6：管控键配置与等价规则（已确认）

- Q3：每张表允许零组或一组并发管控键，一组可含多个字段；未配置时仅保留主键占用。
- Q4：不允许选择自增、生成列及发布时自动填写的字段。新增涉及默认值字段时，管控键值须显式提供；修改未填写的字段沿用真实旧值。无法确定键值时拒绝保存，不能跳过占用。
- Q5：按字段的数据库比较规则判断键值是否相同，包括字符排序规则；NULL作为明确值参与占用，相同的含NULL组合也冲突，NULL与空字符串不同。
- Q6：原值A、草稿拟改B、后改C时，保存成功后保留A和C，释放本单其他明细也不再需要的B；若C被其他单占用，整次保存失败，原草稿及A/B占用保持不变，页面保留输入。

### Q7–Q10：单据范围与容量（已确认）

- Q7：支持一张发布单涉及多张业务表，不沿用此前单表限制。
- Q8：同一发布单内，同一表的同一主键只允许一条明细；不同主键的明细可共享同一管控键占用，由整单共同持有，最后一个引用移除才释放。同一ID在不同表属于不同目标。
- Q9：整单最多1000条明细，多表合计计算；超限明确拒绝，不自动拆单。发布及回滚仍为整单一个事务，交付时用真实数据库验证容量边界。
- Q10：分页只影响查看和编辑，保存可仅提交本次明细增删改，但检查整单版本并原子更新，其他页明细不受隐式替换。另一人修改任意页导致版本冲突时，拒绝覆盖且保留输入；提交审批、发布及回滚始终处理整单。

多表方案调整现有主单单表约束，发布和回滚的明细执行顺序见后续确认；当前部署仍只有一个受管数据源，不因支持多表引入跨数据源事务。


### Q11–Q13：执行顺序与草稿派生（已确认）

- Q11：整单明细具有可调整的明确顺序，提交审批后冻结；发布按正序执行，回滚按倒序执行。不自动猜测或重排业务依赖。
- Q12：复制已取消或已拒绝的单时重新读取当前数据，重新竞争全部占用；任一冲突则整次复制失败，不创建部分草稿，展示占用单号及负责人。
- Q13：重新准备已批准未发布的单时，取消原单、创建新草稿、转移仍需占用及取得新增占用在同一事务内完成；任一失败保留原已批准单及全部占用。新草稿重新审批，不继承原审批。


### Q14–Q17：动态引用、规则变更与执行审计（已确认）

- Q14：本期不支持引用同单新增记录尚未生成的自增ID。跨明细引用的ID必须在保存时已知；自增新增本身仍可使用。
- Q15：只要表被未结束发布单的明细引用，即使还没有具体键值占用，也禁止新增、删除或修改管控键定义。此规则收紧并取代Q2中仅“有在途占用时禁止”的门槛。
- Q16：执行记录只保存成功发布和成功回滚，最多两条；明确失败记录在操作历史，超时先标记结果待确认，确认失败后才能写失败。相同请求重试不新增执行记录。
- Q17：本次回滚执行人或管理员可以事后补填及修改原因，每次保存修改人、时间和内容；原因可选、无期限、不阻塞其他发布。


### Q18–Q20：错误、失败审计与容量（已确认）

- Q18：明确失败后前端报错提示用户，不自动重试；后端接口保证事务和幂等。不得沿用上一轮推荐中的自动恢复或自动重新发起策略。超时不能直接等同执行失败；后续Q21明确不设独立结果确认入口，允许用户重推原操作。
- Q19：只有确认业务事务未提交才能报告执行失败；数据库不可用导致失败历史无法保存时，允许明确提示“失败记录未保存”，不得伪造留痕或为失败审计留下部分业务变更。结果未知继续待确认。
- Q20：本期不采用提出的单请求1MiB、单字段64KiB、整单明细及单次结果8MiB字节上限；保留已确认的整单最多1000条。现有发布单链路中的相关固定大小限制需要按新契约调整，不能使分页、保存、发布或回滚仍被旧预算隐式拒绝；不据此修改无关功能的限制。

### Q21：不增加独立确认入口（已确认）

不提供独立的“确认执行结果”入口或额外确认流程。前端请求异常报错，不自动重试；推进成功则后台主单状态随事务更新，失败则不推进。用户可以再次点击原操作重推；同一业务请求保留幂等身份，后台已提交时返回原结果，未提交时允许原子执行，不能重复生效。事务原子性与请求幂等共同保证重推行为，不能仅凭前端超时声称后台未执行。

此项取代Q18/Q21草案中的专门未知结果确认入口及等待人工确认的前端门禁。正常的请求处理中防重复提交、后台状态/整单版本校验继续有效。

### Q22：整体验收确认（已确认）

用户确认规格综合稿的验收接缝、AC-001～AC-015及非目标，进入规格发布阶段。

## 验收场景草案

验收接缝建议沿用正式发布单页面、表规则页面、已认证Admin HTTP API与真实MySQL；API和数据库验证真实一致性与权限，浏览器验证多表明细分页、冲突提示、排序、恢复差异和历史。

| 编号 | 场景及可观察结果 |
| --- | --- |
| AC-001 | 一张主单管理多表混合明细，列表只展示主单；申请、正向实际结果、逆向实际结果分别保留，成功执行最多两条，无独立回滚单或执行结果明细表。 |
| AC-002 | 管理员为表配置零组或一组单/组合字段管控键；引用真实且保存时可确定的字段，拒绝自增/生成/发布自动字段；存在未结束单的明细引用时禁止增删改定义，规则修改与草稿保存竞争也不能绕过。 |
| AC-003 | 空草稿无占用；明细保存时原子取得表+主键和管控键占用，新增新值、修改旧新值、删除旧值；跨单冲突拒绝且显示占用单号、负责人。同单共享键只持有一份保护，删除最后引用才释放。 |
| AC-004 | 按数据库字段比较语义判键值相等，包括大小写、数值规范化、NULL与空字符串区分及组合字段边界；等价输入不能绕过占用。 |
| AC-005 | 分页增量保存及整单排序使用主单版本；同表主键去重，不同表同ID可共存；并发编辑拒绝覆盖且保留输入。A/B改A/C时原子更新占用，冲突保留原内容和占用。 |
| AC-006 | 整单多表合计最多1000条，1001条保存拒绝；不自动拆单；不采用本轮提出的字节上限，结果与明细不再受旧整单JSON预算挤占。 |
| AC-007 | 提交后冻结明细及顺序，审批和发布期间持续占用；普通审批与权限继续有效。取消、拒绝、完结释放全部目标，管理员可取消遗留草稿，无自动过期。 |
| AC-008 | 复制已取消/拒绝单重新读取并竞争占用，任一冲突不创建部分草稿；重新准备已批准未发布单原子取消、创建和转移占用，失败原单不变，成功新单重新审批。 |
| AC-009 | 多表按冻结顺序一次事务正向发布，业务值、实际结果、各表/记录版本、执行记录、通知、主单和占用一致提交；成功主单待完结，自增新增保护实际ID，不支持引用同单尚未生成的ID。 |
| AC-010 | 当前发布人员在原单预览恢复差异，一次确认免审批整单倒序回滚；成功记录实际逆向结果、原单已回滚并释放全部占用，原始申请和审批历史保留。完结后及已回滚单不能回滚。 |
| AC-011 | 任一明细唯一键/外键/业务值/结构/规则冲突或事务失败时整单不生效；真实失败向前端报错，不自动重试。失败记录写操作历史，不能写入则如实提示，未知结果不伪造失败。 |
| AC-012 | 同键重复不重复执行，回滚/完结竞争只有一个终态；断网或超时前端报错且不自动重试，无独立确认入口。用户重推原操作时同请求幂等处理，已提交则返回原结果、未提交则原子执行；刷新读取实际主单状态。 |
| AC-013 | 回滚执行人或管理员可事后选填、修改原因，记录修改人、时间和内容，其他人不得修改，无期限且不阻塞后续发布。 |
| AC-014 | 页面/API均执行当前权限；多表分页、排序、错误定位、原单结果及历史在桌面和390px可用，键盘可达，沿用现有Web设计规范。 |
| AC-015 | 新库与已有库支持三表及占用结构升级；不做旧发布单数据迁移或旧独立回滚流程兼容，取消旧流程和仅为旧整单JSON存储服务的结构；不自动删除环境数据。 |

## 本方案非目标

跨数据源事务、动态引用尚未生成的自增ID、自动猜测/重排业务依赖、部分发布或部分回滚、完结后回滚、回滚再次回滚、自动重试、独立执行结果确认流程、占用自动过期、每表多组管控键、自动占用所有唯一键、旧单数据兼容、独立执行结果明细表、字段交互改造及下游接收确认。
