# 由表绑定的角色授予审批资格，多表全部通过后才能发布

例如同一发布单同时修改商品表和价格表，运营角色可以负责商品表，财务角色可以负责价格表；用户于 2026-09-09 确认由管理员维护可自定义的审批角色及人员多对多关系，每张表绑定一个或多个角色，任一对应角色成员的一次批准即可满足该表审批。所有涉及表都通过后整单才获批，任何有效拒绝终止整单，同一人可以一次处理其有权审批的多张表。这增加了部分表已通过的进度和多人共同完成的成本，换取不同表由各自负责人员审查，而无需为整单寻找一名覆盖所有表的人。

查看、编辑、发布与平台管理沿用全局账号权限；旧全局 `APPROVER` 不再独立赋予全表审批权，所有人继续禁止自审。正常审批由对应角色成员执行；提交快照未配置角色、角色停用、成员为空或无已启用且不是申请人的成员时，允许当前符合独立审批条件的 ADMIN 默认接手该表。合格成员恢复后，尚未完成的默认 ADMIN 资格退出，已经合法完成的审批保留。申请人若是唯一 ADMIN 且无其他合格成员，不能通过默认规则自审；新提交拒绝，在途申请等待补充合格人员。该默认机制允许管理员在人员配置暂时不可用时接手，代价是需要动态计算和明确展示资格来源，而不是假设 ADMIN 对任何表均有无条件审批权。

这明确调整 [ADR-0019](./0019-require-release-orders-for-managed-record-changes.md) 引入的全局审批授权及[原发布单规格 #48](https://github.com/asherzj/relational-config-center/issues/48) 的单人审批规则，同时作为[多表规格 #81](https://github.com/asherzj/relational-config-center/issues/81) 的后续授权变更；不调整整单发布的原子性或回滚权限。

提交时固定各表的审批角色，后续成员资格按当前状态检查，已合法完成的审批不会因撤权或停用自动作废；之后调整表绑定只影响新提交的申请。相比让审批配置变化重算既有决定，这保证每次申请的审批责任可追溯，又允许新成员接手未完成的工作。需要改换旧申请的审批角色时取消并重新提交。部分表通过后仅剩余待审批表可以继续处理，不能凭已经完成的表资格反复审批或拒绝整单。

本决定是已确认的业务目标，尚未实现。角色维护、旧 `APPROVER` 退出、通知范围、资格变更后的提醒及失败语义均已确认，见[澄清记录](../design-notes/approval-roles-notification-center-discussion.md) Q1～Q12；正式验收和交付安排见[规格草稿](../specs/approval-roles-notifications/spec.md)。
