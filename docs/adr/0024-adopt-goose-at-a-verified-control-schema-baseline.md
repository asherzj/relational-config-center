# Adopt Goose at a verified control-schema baseline

现有数据库升级依赖显式 SQL 和维护命令，历史迁移包含一次性结构修改与业务回填。引入 Goose 管理 RCC 控制表的后续迁移：存量数据库必须先通过当前结构校验才能登记接管基线，更旧的版本先完成既有升级流程；不通过重放整条历史迁移链猜测数据库进度。

生产升级由部署者显式运行独立维护命令或部署任务，Admin 启动只检查版本与结构。首期仅支持向前升级和修复，数据恢复沿用备份流程，不提供 `down` 反向迁移；这保留了升级权限与业务进程职责的边界，并避免把 MySQL DDL 的部分成功误认为可整体事务回滚。

新安装、后续升级和本地 Compose 统一使用 Goose；历史 SQL 只承担旧库升级到接管基线的职责。迁移失败或中断阻止 Admin 就绪及本次部署继续，由维护者核查后显式重试；多个迁移进程有界等待同一把锁，超时退出。

这些选择于 2026-09-09 的 Goose 接入讨论中确认。它们将技术基线中延期的迁移框架引入计划推进为已接受决策，保留 ADR-0001 对业务表结构由部署者负责的范围约定。

T2 将接管基线冻结到 `8b5cd8592f0fbf02dcd27bb72a8a306fa371993d` 的当前控制结构，包含历史 013 的 Policy 审计列改名。保留已发布 00001 内容，追加 00002；接管使用同一维护锁及持久尝试表，在完整结构核查后原子登记版本前缀，不执行迁移 SQL。描述性表注释和表级自增计数不参与结构兼容性判断，列默认值、列注释、索引和约束仍严格比较。接管中断沿用显式恢复入口，内容摘要绑定原基线。

T3 完成部署切换：独立镜像任务执行 Goose，Compose 仅在迁移成功后加载开发 fixture，再启动 Admin；已有卷只允许显式接管和恢复。Admin 启动与 HTTP readiness 共用只读版本、尝试状态、发行摘要和完整控制结构验证，不执行 DDL 或登记版本。当前新安装调用方全部使用嵌入迁移，删除原当前初始化 SQL 与四份局部 Ready 结构清单。冻结的 pre-Goose SQL/数据快照仅承担旧库接管和独立结构预期；历史 SQL/维护命令继续承担旧库升级职责。
