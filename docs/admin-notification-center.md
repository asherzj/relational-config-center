# 通知中心

正式入口为配置管理下的 `/configuration/notifications`，默认“待我审批”。一张发布单显示一行，复用正式发布单详情、逐表审批与原业务操作。视图、表名、单号、状态及分页游标保存在 URL；从详情返回时恢复原筛选与页位置，并读取当前进度。

## 公开读取契约

`GET /api/v1/release-orders?view=pending` 使用当前登录账号与既有部署级 VIEWER 查看权限，不新增审批授权。未提供 `view` 时保留普通发布单目录的既有行为。

| `view` | 范围 |
| --- | --- |
| `pending` | 已提交且当前账号仍有至少一张可审批表的单据；使用详情相同的当前资格规则，排除申请人、已经处理的表和整单终态 |
| `mine` | 当前账号已提交的申请及后续状态；账号来自服务器会话，不能通过 `applicant_id` 冒充他人 |
| `handled` | 当前账号真实执行过 APPROVE 或 REJECT 的发布单；资格撤销、角色停用及后续进度不会删除处理历史 |
| `all` | 本部署所有有 SUBMIT 事实的发布单及后续状态；可查看不代表可审批 |

提交以持久 SUBMIT 事件判断，草稿及从未提交便取消的草稿不进入任一视图。多角色、多表和同一人的多次真实审批均不会产生重复行。历史提交事实与逐表快照是否存在独立；不兼容的旧单沿用正式详情的不可用错误，不能被隐藏为“从未提交”或补造审批责任。本接口不转换旧发布单的结构或执行能力。

四视图均接受 `table_name`、`id`、`state` 精确筛选，以及 `after` 与 `limit`（1～100，默认 20）。`applicant_id` 可进一步缩小查询范围；`mine` 中若与当前账号不一致，返回 `422 release_invalid`。空或未知 `view`、非法状态及分页大小同样返回 422。

响应沿用 `{ "orders": [...], "next_cursor": "..." }`，每项保留真实逐表 `approvals`、当前账号专属 `approval_context` 和 `allowed_actions`。按不可变单号升序分页。服务端在同一个 MySQL 一致只读事务中读取候选与当前角色/人员资格，先完成筛选再生成公开页；内部扫描越过无资格候选，返回游标是最后一条已返回可见单的 ID。只有确有下一可见项才提供 `next_cursor`，因此满页末尾也不会制造空的下一页。不同请求间资格和进度可以发生变化，刷新和详情读取会反映最新事实，审批提交继续核对确认范围与版本。

候选扫描采用有限批次，内存中最多保留一页和一个后继条目。当前没有新增查询索引，待审批候选多且当前用户资格稀疏时会增加读取成本；后续优化必须继续复用同一资格规则并保证筛选先于分页。

数据库或资格目录失败返回 `503 release_unavailable`，不能视为没有合格成员或空列表。Web 保留同一查询最近成功的数据，显示错误及重试；新查询在成功前显示加载，不虚构空态。所有请求继续经过既有会话、账号隔离和 no-store 边界。

## 交付边界

#95 只交付真实四视图，未新增持久通知、未读计数、已读动作或定时刷新。个人待办/未读与业务事务接入由 #96 负责，后续发布结果提醒由 #97 负责；列表读取不创建通知事实。使用已有 Goose 00007 结构，不修改已发布迁移，不新增初始化或旧数据清理路径。
