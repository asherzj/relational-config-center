# 通知中心

正式入口为配置管理下的 `/configuration/notifications`，默认“待我审批”。一张发布单显示一行，复用正式发布单详情、逐表审批与原业务操作。视图、表名、单号、状态及分页游标保存在 URL；从详情返回时恢复原筛选与页位置，并读取当前进度。

## 公开读取契约

`GET /api/v1/release-orders?view=pending` 使用当前登录账号与既有部署级 VIEWER 查看权限，不新增审批授权。未提供 `view` 时保留普通发布单目录的既有行为。

| `view` | 范围 |
| --- | --- |
| `pending` | 已提交且当前账号仍有至少一张可审批表的单据；使用详情相同的当前资格规则，排除申请人、已经处理的表和整单终态 |
| `mine` | 当前账号已提交的申请及后续状态；账号来自服务器会话，不能通过 `applicant_id` 冒充他人 |
| `handled` | 当前账号真实执行过 APPROVE 或 REJECT 的发布单；资格撤销、角色停用及后续进度不会删除处理历史 |
| `all` | 本部署所有有 SUBMIT 事实的发布单及后续状态；可查看不代表可审批 |

提交以持久 SUBMIT 事件判断，草稿及从未提交便取消的草稿不进入任一视图。多角色、多表和同一人的多次真实审批均不会产生重复行。历史提交事实与逐表快照是否存在独立；不兼容的旧单沿用正式详情的不可用错误，不能被隐藏为“从未提交”或补造审批责任。本接口不转换旧发布单的结构或执行能力。

四视图均接受 `table_name`、`id`、`state` 精确筛选，以及 `after` 与 `limit`（1～100，默认 20）。`applicant_id` 可进一步缩小查询范围；`mine` 中若与当前账号不一致，返回 `422 release_invalid`。空或未知 `view`、非法状态及分页大小同样返回 422。

响应沿用 `{ "orders": [...], "next_cursor": "..." }`，每项保留真实逐表 `approvals`、当前账号专属 `approval_context` 和 `allowed_actions`。按不可变单号升序分页。服务端在同一个 MySQL 一致只读事务中读取候选与当前角色/人员资格，先完成筛选再生成公开页；内部扫描越过无资格候选，返回游标是最后一条已返回可见单的 ID。只有确有下一可见项才提供 `next_cursor`，因此满页末尾也不会制造空的下一页。不同请求间资格和进度可以发生变化，刷新和详情读取会反映最新事实，审批提交继续核对确认范围与版本。

候选扫描采用有限批次，内存中最多保留一页和一个后继条目。当前没有新增查询索引，待审批候选多且当前用户资格稀疏时会增加读取成本；后续优化必须继续复用同一资格规则并保证筛选先于分页。

数据库或资格目录失败返回 `503 release_unavailable`，不能视为没有合格成员或空列表。Web 保留同一查询最近成功的数据，显示错误及重试；新查询在成功前显示加载，不虚构空态。所有请求继续经过既有会话、账号隔离和 no-store 边界。

## 交付边界

#95 交付四视图；#96 接通个人待办、未读、确认已读及前台刷新；#97 接入发布、完结、原单回滚及重新准备取消的结果提醒。列表读取不创建通知事实；当前结构由 Goose 00008 提供，不修改已发布迁移，不新增初始化或旧数据清理路径。

领域与审批规则见 [Admin 词汇表](../admin/CONTEXT.md)、[表审批决策](adr/0026-authorize-approval-by-table-roles.md)及[发布审批契约](admin-release-approvals.md)。桌面、390px 和键盘验收见 [功能验收报告](verification/approval-roles-notifications.md)。

## 个人提醒与已读

`GET /api/v1/approval-notifications` 只读取当前登录账号的 `{ "unread_count": 2, "pending_count": 1 }`。个人未读入口链接 `?view=all&unread=true`；四个视图都可以叠加 `unread=true`，服务端仍在筛选完成后分页。未读数量按账号和发布单聚合；读取后待审批数量不会减少，只有当前可审表全部消失才移除待办。尚未成功读到计数时不显示伪造的零。

主单详情及列表每项增加 `notification: { "sequence": "3", "unread": true, "pending": false }`。无提醒为 `sequence: "0"`。序号是无符号整数的十进制字符串，Web 不将它转换为 JavaScript Number。详情主单、当前审批资格和这份个人进度来自同一 MySQL 一致只读快照，因而可以表达没有修改发布单版本的资格变化。

业务写响应保留原请求结果的独立契约，不提供已读依据；重新读取成功的详情才可确认进度。

详情成功展示后，以该响应中的序号调用 `POST /api/v1/release-orders/:id/notification-read`，正文仅 `{ "sequence": "3" }`，响应为最新个人 `notification` 对象。请求始终确认当前会话账号，不接受收件人参数；沿用 CSRF、同源保护和账号代次校验。已读位置只向前推进至本次指定序号，超出目前序号拒绝 422；重复或迟到确认不影响更晚的通知。不能先读取最新通知序号，再替早先展示的详情确认。此接口本身自然幂等，无业务请求键，也不会执行任何审批。

已读失败保留未读和已显示的详情，提供重试；手动重试仍使用实际显示的序号，不自动接着确认响应中的新序号。详情失败不进行已读确认。普通业务写入仍沿用原键、原正文的人工作业重推，不自动重放。

## 事务与资格变化

提交给当前合格审批人员生成待办；每次部分/全部批准、拒绝、已提交申请取消给申请人更新进展。动作本人不会因此获得新的自身提醒，也不清除过去尚未阅读的他人变化。角色数、表数不会放大个人单据计数。

个人记录分别保存待办状态、纯待办进度、结果进度及已读位置。成员增删、角色启停、账号启停、ADMIN 资格变动，均在原资格维护事务中按提交快照和实时成员重新核对未完成申请。普通会话活动不会触发这项扫描，GET 不补造通知事实。失去最后可审表只移除纯待办未读；申请、真实处理历史及结果未读保持原义。所有资格判断复用审批动作的同一规则，表后来改绑不替换旧单的责任。

通知与业务变化、审批事实及原请求结果同事务保存，数据库写入故障整笔回滚；响应丢失不等于失败，原业务请求重推只恢复原结果。个人通知由正式 `00008_approval_notifications.sql` 与完整 `00008_schema.json` 管理，`rcc_` 控制表保护阻止通用数据能力管理它；它与下游 `rcc_refresh_notifications` 有各自独立含义。

发布、完结与原单快速回滚成功后，结果提醒发给申请人及保存的逐表审批决定者，按永久 Account ID 去重并排除本次操作者。普通角色与默认 ADMIN 的真实决定者同样保留；后来退出角色、停用账号或新成员接替，不会改写这份参与关系。单纯发布过或可以查看的人不会因此成为结果收件人。完结不产生新的执行、业务变更或下游刷新记录，但仍推进个人结果提醒。

重新准备把源单取消、新草稿、目标流转及原请求结果一起保存，取消提醒只给源申请人并排除操作者。新草稿未提交时没有待审批或结果提醒；其动态展示的审批安排不代表已经发生提交。复制和修改回滚原因不会重复发送生命周期成功提醒。

这些路径在已有业务事务成功改变单据并保存后、完成原请求结果前，调用 `ReleaseOrderSession.RecordApprovalNotifications(ctx, order, actor, resultRecipients)`。该接口同步当前待办，对去重后的结果收件人推进一次序号；必须由已经完成原请求去重的事务调用一次。通知失败使原事务全部回滚，失败历史不生成成功提醒；HTTP 或 COMMIT 回包丢失后原键原正文重推恢复已保存结果，不增加通知或重复执行。个人读取进度仍只存在读取 DTO，不进入主单或原请求结果。

## 刷新和会话

进入、返回页面和手动刷新会读取最新列表与计数，前台停留每 30 秒更新；后台页面与会话不可读时停止这些保护查询。读取错误保留最后成功数据及明确错误。保护工作区可能保留隐藏子树，因此轮询不依赖组件卸载停止；账号切换清理旧查询空间，响应沿用 API client 的账号 generation 与 `X-RCC-Account-ID` 检查。
