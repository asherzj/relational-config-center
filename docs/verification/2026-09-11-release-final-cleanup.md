## 最终接口与真实反例

普通 `GET /release-orders/:id` 只读取当前主单摘要。`/details?expected_version=…&offset=…&limit=…` 在 MySQL 只读一致性事务内核对整单版本并限制实际明细读取。Web 普通详情与结果每页 20 项，跨页版本变化返回 409，不能静默拼接；编辑、复制和全局排序等确需完整申请的动作显式收集同一版本的页。事务内整单执行及原成功请求结果重建保留必要全量，容量仍是多表合计最多 1,000 项。

真实 HTTP 用例先证明 21 项主单不带 items、20+1 分页，标题变更后旧版本页 409、新页成功和非法范围 422；再执行两表发布/倒序回滚，核对每页结果归属、不可变原申请/发布、旧键返回原成功确认但当前主单仍已回滚，以及撤销发布角色后禁止重推。交换同执行同表不同记录的发布结果或删除正向/逆向结果的明细身份，均返回 503。

每个实际 Command 沿共享执行器携带原有稳定 `detail_id`，读取时与所属原明细绑定。不能用申请 id 的原始字符串近似 MySQL 身份等价：FLOAT、负零等真实用例必须继续合法；独立的规范行 ID、冻结 schema、校验和、执行归属以及原发布/回滚实际身份检查仍保留。缺失逐项表名的增量保存、复制及重新准备均为 422，八张发布控制表不变。

移除主单单表默认、内部整单结果外观及固定 JSON 预算、独立回滚路由/字段/DTO/UI 关联、旧未知结果确认残留。保留明确冲突审阅、原账号/键/完整正文手动重推、最新主单状态与当前权限、本地输入和 journal。文档区分当前 Goose 与未接管历史人工链，没有旧发布单业务数据转换或环境清理。
