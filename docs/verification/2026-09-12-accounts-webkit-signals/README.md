## Exact tracing boundary

The temporary PR-111-only job installs the locked Playwright WebKit and strace, then uses the original reviewed 12-round generator unchanged. Every round calls the original accounts case in its own Node process/profile against shared real services. The first failed round stops execution; the original case limit remains 600 seconds and the job remains 15 minutes, including setup. There are at most 12 attempts, never a retry of a failed case. Formal CI's original eight jobs and the original browser runner/accounts source remain byte-identical to the base.

`diagnose-accounts-webkit-signals.sh` obtains the installed WebKit executable through Playwright, saves its SHA and mode, and copies it to the same directory with `.rcc-110-original` appended. The temporary entrypoint uses `exec strace` to invoke that unchanged original launcher with exactly its supplied arguments. Thus only the WebKit process tree is traced; Node, Go builds, service processes and Docker/MySQL execution are not ptraced. The EXIT trap copies back the original mode/content, checks byte equality, records the restored SHA and preserves the runner's original exit status. Restoration errors remain visible on stderr. An existing failed runner status is preserved; restoration failure after a successful runner instead fails the diagnostic job with status 1. Both SHA and mode must match before/after. Forced runner-host destruction cannot guarantee a shell trap runs; this cache is isolated to the disposable diagnostic job and is not persisted by a browser-cache action.

The only selected syscalls are `exit,exit_group,wait4,waitid,kill,tgkill`; all delivered signals are reported. `-f -ttt --decode-pids=comm -o` follows descendants from launch, including renderers, writes epoch timestamps and process-name prefixes, and creates one uniquely named trace per browser launch. No `execve`, argv, environment, read/write payload, general syscall listing, stack or memory/core dump collection is enabled. Names are process `comm`, not command lines. Signal records can carry OS metadata such as sender PID/UID and a fault address; these do not constitute a stack or memory dump. A sender outside the traced browser tree may have PID/UID without its full causal history. OS signal tracing does not guarantee identification of every IPC failure or a native root cause.

`-f` rather than `-ff` is deliberate: Ubuntu strace 6.8's split-file output lacked process-name prefixes, and it does not support the newer `--always-show-pid` option. A per-launch combined file retains clear `WPEWebProcess` identity with the same syscall whitelist and child-following coverage. The [strace project](https://github.com/strace/strace) documents PID-name decoding and child tracing. ptrace changes timing, even with a narrow output filter; both a failure and a pass must be interpreted with that limitation. Local architecture is arm64; the actual diagnostic job is native amd64. No formal-case semantics are changed to accommodate tracing.
