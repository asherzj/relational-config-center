## 完整回归暴露的测试环境问题

首轮全量失败后，以两个原用例组成 25.511 秒的短回路，稳定复现 `TestAccountProcessRestartPreservesSessionsAndRateWindows` 中 Python 会话脚本的首次本地请求连接关闭。相同测试权限环境中启用 HTTP/HTTPS 代理且没有绕过回环地址；只加本地 `NO_PROXY/no_proxy` 后原用例通过（16.274 秒）。修复将绕过限定在该测试子进程，生产脚本及业务行为不变。

`TestMutationPolicyAutoFillUsesAccountOperatorAndDatabaseTimeAndRejectsManagedInput` 原先用宿主机时间 ±1 秒校验 MySQL 生成的时间；全量运行实际出现数据库值超出上界 87.839 毫秒。断言改为使用同一 MySQL 的 `UTC_TIMESTAMP(6)` 在请求前后取样，保持“由数据库在请求期间生成”的严格断言，避免跨宿主机与虚拟机时钟比较。

这两个原用例修复后一起通过（22.702 秒）。首轮 40 分钟超时发生在整套测试尾部、正常等待新容器启动时，故正式 Makefile 的集成预算增至 50 分钟，CI 对应作业增至 55 分钟；没有增加迁移命令或业务请求的超时。第二轮完整验证使用 `go test -json -failfast -count=1 -timeout=50m -tags=integration ./...`，逐条记录实时结果，已全部通过（545 项，0 失败、0 跳过）。

追加评审发现 MODIFY Auto Fill 也使用宿主机时间断言，已同步改为同库时间窗口；最终 `TestMutationPolicyPatchAutoFillUsesModifySlotsAndRejectsManagedInput` 真实 MySQL 补跑通过（10.789 秒）。第二轮完整回归在这处追加测试修正之前已构建，因此最终 MODIFY 断言以此独立补跑为证据；生产代码、其余测试均包含在第二轮构建中。新增测试/预算差异已经双轴复核，最终均为 0 项未解决发现；Standards 指出的技术选型表旧表述亦已同步。

## 测试先行记录

先验证新命令不存在导致初始化失败，再逐个补齐实现。锁超时验收最初发现 Goose `Up` 在锁外初始化版本表，改为逐个 `ApplyVersion` 并让同会话锁先于全部写入；普通并发用例最初已经通过，调查确认不足以单独证明锁生效，因此增加独立持锁会话的有界冲突测试。

随后分别观察并修复：部分 DDL 失败被当作普通 pending、目标结构清单导出连接字符集不一致、下一发行版本要求被写死、确认失败被已应用版本哨兵错误掩盖、缺少首次尝试的初始化无法恢复、同版本改写 SQL 仍可恢复、缺失中间版本仍被当作 current、空 Goose 版本表缺失零记录、控制表继承数据库默认字符集，以及恢复误执行后续版本。MySQL 授权和触发器创建前置条件失败先修正测试条件，没有把它们当成功能失败证据。连接超时用例在既有驱动行为下直接通过，没有为制造红灯改坏实现。
