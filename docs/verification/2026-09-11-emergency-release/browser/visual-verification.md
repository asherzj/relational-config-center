# 应急发布真实浏览器及视觉核对

用户在阅读 `../browser-approval-plan.md` 所列目标、操作和风险后明确同意继续；授权记录见 `../browser-authorization.md`。原始拒绝、失败和第一次全绿结果保留，不覆盖。

## 实际系统路径

`01-run.log` 为真实失败：已经发布成功后，脚本等待了早已存在的状态文字，未等原提交重推实际响应便断言请求次数。脚本改为等待公开 POST 200 和提交窗口关闭，再比较原键、原正文以及正常读取的当前详情。`01/run-notes.md` 记录原始故障及首次容器身份捕获失败。

`02-run.log` 为 PASS。视觉核对发现三个浮层截图使用 full-page，且旧草稿保存提示暂时遮住底栏，因此保留该批，并补 `03`：等待成功提示自然消失，浮层使用真实 390×844 视口截图；未隐藏或删除任何产品元素，生产源码未改变。

`03-run.log`、`03-run.json` 为最终系统路径 PASS，运行期间源码变化为空。运行前 `03/source-input.json` 包含所有 Admin、Web 源码与新浏览器脚本的散列。`03/runtime-target.json` 记录本次新建 `rcc_test` 数据库地址及 Admin/Vite 地址和进程；`03/container-inspection.json` 将该端口绑定到新 `mysql:8.4` 容器完整 ID；`03/cleanup.json` 确认本轮容器已不存在、Admin/Vite/测试进程均已退出，既有预览容器保持原样。

`03/release-emergency-browser-evidence.json` 保存两表在应急→常规→应急时的实例身份、最终真实节点和历史、编辑与提交的原键及原正文。每表的每次明确切换均产生新实例，未知编辑重推保持已保存的原实例。提交不写业务、不产生审批；当前申请人具备发布权限时可手动整单执行，两表业务值和版本同时生效。完结前保留回滚入口，完结后入口消失且值/版本不变，新草稿可重新占用两表目标。

七张 `03/*.png` 均已直接打开核对。

| 图片 | 核对结果 |
| --- | --- |
| `emergency-draft-desktop.png` | 桌面基本信息和动作并列；两表各自展示保存的两节点流程；标题、模板名和人员身份完整可读；应急无最近审批人。 |
| `emergency-reason-mobile.png` | 390×844 下原因标签、字符计数、完整申请差异、关闭及确认按钮清楚可见；输入焦点环可辨认，底栏未被提示遮住。 |

| `emergency-session-interrupted-mobile.png` | 会话退出并刷新后只显示登录表单，业务浮层没有穿透；同账号登录后从持久请求恢复原原因和原提交。 |

自动浏览器断言还核对空白与 2,001 个 emoji 的原因不发提交请求、手机页面没有横向溢出、未保存确认默认焦点、原包两次请求完全相同，以及提交前后、发布和完结后的真实公开业务查询。该脚本不是权限矩阵或数据库故障覆盖的替代，这些事实由本票 38 个真实 HTTP/MySQL 用例承担。

最终双轴审查在 `03` 之后要求补充确定冲突重建的读取门禁和成功提示；该路径不在本浏览器的“未知结果原包重推”流程中。后续仅修改 `ReleaseRequestReview.tsx` 及其页面测试，以公开 UI / fetch 契约测试补验失败预览、再次读取失败、资格变化、成功与未知反馈，并复验其共享消费者；`03` 对其余未变输入继续有效。
